## 0. 结论前置

### 0.1 五个必须表态的设计决策

| # | 议题 | 结论 | 一句话理由 |
|---|---|---|---|
| ① | **指标卡在合并楼层里是否降级？** | **降级 —— 但降的是「卡壳」不是「字号」。** 3 张卡从「横排 4 张」改为「左侧纵向 3 卡轨」（`lg=8`），`Metric` 新增 `compact` 变体：value 仍 **22px/500**（守住 §4.1 黄金三角），只把 padding `14→12`、间距 `6→4`。**楼层 1 总高从 381px 降到 310px，省 71px ≈ 2 行表格。** | 争高度的从来不是字号，是排布方向。字号降了就破坏「指标带」的契约。 |
| ② | **趋势图堆叠 vs 并列？** | **堆叠（stacked），交付在下 / 运维在上，段序恒定。** | 堆叠的总高 = 当月合计，一个高度读一个数，正是「全局视角」；并列要读两根柱再心算，且 12×2=24 根柱在 692px 内每根仅 14px，低于可读阈值。**代价**：运维段无统一基线、不可直接横向比较 —— 已记录。 |
| ③ | **累计态如何表达？** | **三件套：① BlockTitle 右侧一枚胶囊徽标 `● 累计 · 截至 2026-08`（复用 `filterChipBg` + `filterDot`）；② 全部 12 根柱满色、无选中标记；③ 待出账月份用「空心状态点」+ 图例注明「不计入累计」。** 「柱下方选中标记条」被完整保留给单月态，两态在视觉上互斥。 | 累计不是一个「更模糊的单月」，它是一个**不同口径**。口径必须有一个常驻的、非 hover 依赖的锚点。 |
| ④ | **列表两种态的列结构** | **两态共用同一份 `COL_WIDTHS`（4 列 / 680px / `scroll.x` 派生）。** 单月态 = 该月各部门的账单行；累计态 = 各部门一行汇总。列不随月份切换而跳动。 | 列宽表只有一份 ⇒ 从结构上消灭「两态列宽不一致导致切月时列跳动」这类缺陷。 |
| ⑤ | **「指标卡 vs 趋势图」谁是主体？** | **同层并列，指标在左、趋势在右（不是上下）。** 决定性理由：③ 要求「点柱 → 指标联动」，上下排布时指标被推到视口外，用户点了柱看不到数变。 | 联动的可观测性决定排布方向。 |

### 1.2 新增清单（**恰好 1 条**）

| 令牌 | 取值 | 用途 | 为什么既有键不够 |
|---|---|---|---|
| `trendIdleOpacity` | `0.42` | 趋势图**非当前柱**的整体降透明度（柱段 + 月份标签 + 状态点三者必须同值，否则会各自漂移） | `useT()` 现无任何 opacity 类令牌。现状把 `0.55 / 0.35` 两个数硬编码在 `Trend` 组件内（`BillingModule.jsx:105-106`），既无出处也无论证，且「0.55/0.35」这两个值之间的差值关系不可追溯。提升为令牌并锁定为**单值** `0.42`，同时消除「两段用不同透明度导致看起来像两种深浅的品牌色」这一既存视觉歧义 |

> **未新增颜色令牌的论证**：本轮唯一的颜色决策是「运维段用什么色」。既有 `c.info` 不可用 —— `main.jsx:19` 显式设 `colorInfo: '#005BAA'`，与 `colorPrimary` **同值**（探针实测 `colorInfo = #005baa`）。这意味着**现状趋势图的「交付 / 运维」两根柱其实是同一个颜色**，只靠 `opacity 0.55` 与 `0.35` 区分 —— 这是一个既存缺陷（详见 §5 风险 6）。选 `meterCommitted`（`#7FA8CC`）的理由：① 它是全站唯一登记的「次级实色」，与 `meterBilled`（= brand）已构成一组经生产验证的「主段 / 次段」配色；② 总览页**不含 `PoolMeter`**（§3.5 已论证移除），因此不存在同页同色异义；③ 复用 = 零新增。**代价已记录**：2.51:1 低于 WCAG 非文本 3:1，以「段序固定 + 图例文字」作为第二重通道补偿（§4.4）。

### 1.3 指标卡着色方案（替代现状的「彩虹 KPI」）

现状 3 张卡是 `brand` / `success` / `brand` 三个颜色 —— 违反 DESIGN §5 陷阱 1（彩虹 KPI 卡）与 §4.4-2（只有需要被注意的金额才染色）。本轮改为：

| 卡 | 数字色 | 对比度 | 说明 |
|---|---|---|---|
| ① 交付计费 | `brand` `#005BAA` | 6.83:1 ✅ | 全楼层**唯一被染色的金额** |
| ② 运维计费 | `t1` | ≈13:1 ✅ | 纯信息，不染色（`tone="plain"`） |
| ③ 合计应收 | `t1` + **左侧 3px `brand` 竖条** | ≈13:1 ✅ | 「主」由位置（第三张）+ 竖条表达，不靠给数字上色（§2.3 允许「只允许左侧 3px 强调条」） |

**「一屏染色金额 ≤ 3」自查**：交付卡数字 1 处（竖条非金额）→ **1 处 ✅**。现状是 3 处。

**不采用「运维卡也上色」的理由**：`meterCommitted` 对白底 2.51:1，**不达 WCAG AA 正文级 4.5:1**，一个 22px/500 的金额数字用这个颜色是不合格的。趋势图里它只作**色块**（要求 3:1，且有第二重通道），指标卡里它是**数字**（要求 4.5:1）—— 同一令牌在两种载体上的合规门槛不同，不能混用。

## 2. 楼层 1（合并层）版式规范

### 2.1 区块构成与网格

```
┌─ Content (padding 16 24 32) ─────────────────────────────────────────┐

│ ── marginBottom 12 ────────────────────────────────────────────────── │
│ Row gutter=[12,12]  ← 楼层 1 单行，align-items 默认 stretch             │
│ ┌── Col xs=24 lg=8 ────────────┐ ┌── Col xs=24 lg=16 ──────────────┐ │
│ │ ① 交付计费   22px/500 brand │ │ ▸ BlockTitle                    │ │

│ │ ② 运维计费   22px/500 t1    │ │ ── 绘图区 高 120 ────────────── │ │
│ │    按订单量/会员规模/固定年费│ │  ▁▃▅█▂▁▃▇█▂▁▃  ← 堆叠 12 柱   │ │

│ └─────────────────────────────┘ └─────────────────────────────────┘ │
│ ── marginBottom 12 ────────────────────────────────────────────────── │
```

### 2.2 列宽核算式（**逐项写出，含两次历史事故项**）

```
有效可用宽 = 视口 − Sider(展开 224 / 折叠 64) − Content 左右 padding(24×2=48)
           − Card body padding(16×2=32) − 竖向滚动条(15)
```

> ⚠️ 后两项是本项目**两次横滚事故的根因**（v0.8 漏算 Card body padding、v0.8.2 漏算竖向滚动条），必须逐项出现，不得写成「大致够」。

| 屏宽 | Sider 展开 | Sider 折叠 |
|---|---|---|
| 1280 | 1280 − 224 − 48 − 32 − 15 = **961** | 961 + 160 = **1121** |
| 1366 | 1366 − 224 − 48 − 32 − 15 = **1047**（设计基准） | **1207** |
| 1440 | 1440 − 224 − 48 − 32 − 15 = **1121** | **1281** |

楼层 1 内部（`Row gutter=[12,12]`，antd Col 用百分比 + 负 margin）：

| 屏 | 左 Col lg=8 | 右 Col lg=16 | 12 槽位宽 | 槽位留白 | hover 底 40px |
|---|---|---|---|---|---|
| 1280 | 8/24×961 − 6 = **314** | 16/24×961 − 6 = **635** | 635/12 = **52.9** | (52.9−24)/2 = **14.5** | 40 < 52.9 ✅ |
| 1366 | 8/24×1047 − 6 = **343** | 16/24×1047 − 6 = **692** | 692/12 = **57.7** | **16.9** | ✅ |
| 1440 | 8/24×1121 − 6 = **368** | 16/24×1121 − 6 = **741** | 741/12 = **61.8** | **18.9** | ✅ |

> **判定**：柱宽固定 24px，在三档屏下留白均 > 14px，hover 底（40px）永不与相邻柱重叠。**不做「柱宽随容器等比缩放」** —— 那会让宽屏柱变肥、窄屏柱变瘦，趋势的形状失真。

### 2.3 高度核算式

```
Metric（compact）= padding 12×2=24 + label 12px/1.5=18 + gap 4
                 + value 22px/1.2=26.4 + gap 4 + sub 12px/1.5=18 = 94.4 ≈ 94
左轨总高 = 3×94 + 2×8(gap) = 298

趋势卡 = padding 16×2=32
       + BlockTitle 14px/1.5=21 + marginBottom 12 = 33
       + 绘图区 paddingTop 8 + 柱区 120 + 轴标签行(marginTop 6 + 11px/1.4=15.4) = 141.4
       + 脚注行(marginTop 12 + paddingTop 12 + border 1 + 12px/1.5=18) = 43
       = 257.4 ≈ 257

Row 高 = max(298, 257) = 298   （趋势卡 height:100% 撑满）
楼层 1 = 298 + marginBottom 12 = 310
```

**对比现状**：

```
现状 = 趋势卡 267（32+33+159.4+43，其中 159.4 = 8+120+6+15.4+4+6 状态点单独占一行）
     + marginBottom 12
     + 指标行 102（padding 14×2=28 + 18 + 6 + 26.4 + 6 + 18）
     = 381
```

| 项 | 现状 | v1.4 | Δ |
|---|---:|---:|---:|
| 楼层 1 总高 | 381 | **310** | **−71px（≈ 2 行紧凑表格）** |
| 首屏可见表格行数（1440×900 估） | 6 行 | **8 行** | +2 |

> **顺带收益**：把状态点从「标签下方单独一行」改为「标签前缀」（`● 2026-01`），省 10px，并消除圆点与标签之间的视觉脱节。

### 2.4 三档屏与降级

| 断点 | 布局 | 说明 |
|---|---|---|
| ≥ 1440 | `lg=8 / lg=16`，柱高 **120** | 有余量可把柱高提到 132，**但不同屏不同柱高会破坏跨屏的视觉记忆**，判定为**不变量** |
| 1366（基准） | `lg=8 / lg=16`，柱高 120 | 所有数值以此为基准 |
| 1280 | `lg=8 / lg=16`，柱高 120 | 槽位 52.9px，仍达标 |
| **< 1200** | 两栏均改 `xs=24`（纵向堆叠）；**柱宽 24→20、hover 底 40→32** | 此时 1024 屏右栏仅 464px、槽位 38.7px < hover 底 40px 会重叠。**代价**：楼层 1 高度回到 ~375px（≈ 现状）。**判定**：本项目设计基准是 ≥1280（DESIGN §2.4.2「内部后台，≥1280 铺满」），此档只保证不破版 |
| **< 992（`xs`/`sm`）** | 两栏 `xs=24` 纵向堆叠；**3 张指标卡从纵向 3 行改为横向 3 列**（`Row gutter 8` + `Col xs=8`） | 否则首屏只剩 3 个数字，违背 §4.1。横向时每列 ≈285px，22px 数字放得下 |

### 2.5 指标卡：紧凑型变体的确切规格

`Metric` 新增可选 prop `compact`（**缺省 `false` = 现状尺寸不变**，保证其他 6 个页面零影响）：

| 项 | 现状 | compact | 理由 |
|---|---|---|---|
| padding | `14px 16px` | `12px 16px` | 3 张纵向排列时，padding 是唯一可压的量 |
| label | 12px `t3` | **不变** | |
| label→value 间距 | `marginTop: 6` | `4` | |
| value | 22px / 500 | **不变** | §4.1 要求指标带「一眼看到」，降字号即破契约 |
| value→sub 间距 | `marginTop: 6` | `4` | |
| sub | 12px `t3` | **不变** | §4.4-3 口径必须可见 |
| 左侧强调条 | — | 仅第 3 张卡有，3px `brand` | 替代「给数字上色」表达主口径 |

**代价**：紧凑态下卡片内 3 段文字（18 + 26.4 + 18 = 62.4）占 padding（24）的比例升高，视觉上比现状略紧。这是可接受的 —— 3 张卡纵向排列本身已经通过「位置分组」表达了它们的关联，紧凑只是让整组能塞进趋势卡的高度。

### 2.6 趋势图新交互规范

#### 2.6.1 图表形态：堆叠，段序恒定

| 项 | 规格 | 理由 |
|---|---|---|
| 类型 | **堆叠柱** | 柱总高 = 当月合计，一个高度读一个数 |
| 段序 | **下 = 交付计费（`brand`），上 = 运维计费（`meterCommitted`）** | 交付是变动成本、波动大，必须坐在 0 基线上才可读；运维近乎等高，放上面不损失信息 |
| 段间 | 1px `bg1` 间隔 | 两色相邻时需要硬边界，否则在 2–4px 的细柱上会糊 |
| 运维段底 | 2px `t4` 描边 | 补偿 2.51:1 的对比度不足 |
| 柱宽 | **24px 固定**（<1200 屏 20px） | 见 §2.2 |
| 槽位 | `flex: 1` 均分 | |
| hover 底宽 | 40px（<1200 屏 32px） | 比柱宽一圈，肉眼可见 |
| 圆角 | 仅**最上段**顶部 `3px 3px 0 0` | 堆叠柱只在顶端收角 |
| Y 轴刻度 | **不画数值刻度** | 12 柱 + 一条 0 基线已足够；刻度会吃掉 692px 的宽度。单位写在 BlockTitle 脚注「单位：万元」（DESIGN §4.3 要求的「基准与口径」） |
| 网格线 | **不画水平网格线** | 会与柱边缘、状态点产生视觉噪声。替代：底部一条 1px `borderStrong` 的 **0 基线** |
| Y 轴 max | **固定 = 全部 12 个月 `total` 的 max**，不随选中态变化 | 若随选中变化，点柱会让所有柱缩放跳动，破坏可比性。现状已是如此，**必须保持** |
| 零值月 | `total = 0` 时画 2px 高 `meterTrack` 底线（不画段） | 让用户知道「有月份、没金额」，而不是「这里缺一块」 |
| X 轴标签 | **`● 2026-01`（全串，不是 `01月`）** @11px | `692/12 = 57.7px` 放得下 `2026-01`（≈47px）。全串不依赖「同一年」这个隐含前提；状态点前置使其与月份成为一个整体 |
| 状态点形状 | 已核销 = **实心圆** `success`；已发出 = **半实心**（`success` 环 + `bg1` 心）；待出账 = **空心圆**（`t4` 环 + `bg1` 心） | 形状是颜色之外的第二重通道，灰度打印/色觉障碍下仍可辨（§4.5） |

#### 2.6.2 三态视觉区分

| 态 | 柱本身 | 槽位底 | 选中标记条 | 月份标签 | 光标 |
|---|---|---|---|---|---|
| **累计态**（默认，`picked = null`） | 满色，两段 `opacity: 1` | 无 | **无** | 11px `t3` / 400 | `pointer` |
| **hover**（未选中柱） | **不变色、不变透明度** | `fill` 底，40px 宽，radius 4 | 无 | `t3 → t1`（不加粗，避免与选中混淆） | `pointer` |
| **选中态**（`picked = m`） | 满色 + **柱顶 2px `brand` 顶盖**（宽 = 柱宽） | `brandBg` 底 | **柱下方 3px × (40−12) `brand` 圆角横条** | 12px `brandText` / **500**（升一档） | `pointer` |
| **非选中柱**（选中态下） | 两段同时降到 `trendIdleOpacity (0.42)` | 无 | 无 | `t3` / 400 | `pointer` |

**关键设计约束**：hover **绝不改柱色或透明度**。若 hover 与选中都用「变色」表达，两种语义会互相污染（用户分不清「我现在 hover 的是选中柱吗」）。hover 只用**槽位底**，选中只用**标记条 + 顶盖 + 标签升级**。

**为什么选中标记条用 `navActiveIndicator`（`2px solid brand`）**：它是全站已有的「当前项」标记语言（一/二级导航当前项下划线），此处标记的是「当前选中柱」—— 同一套视觉符号表达同一类语义，用户不需要学新东西。**这是「延续既有规范」最直接的一处。**

#### 2.6.3 「点同一柱取消」的可发现性 —— 四重冗余，不靠单一手段

这是本轮最难的可发现性问题。用户在「点柱选中」之后，**没有任何线索告诉他再点一次会取消**。四重手段：

| # | 手段 | 何时可见 | 为什么必要 |
|---|---|---|---|
| 1 | **常驻状态说明行**（12px `t3`，绘图区下方，随状态改写文案）<br>· 累计态：`点击柱查看该月 · 再次点击同一柱可回到累计`<br>· 单月态：`再次点击 2026-08 可回到累计视图`（月份用 `brandText`） | **始终可见**，不依赖 hover | 唯一「零学习成本」的手段。绝大多数误操作来自「用户根本不知道有这个功能」 |
| 2 | **选中标记条 + 顶盖**本身 | 选中后 | 选中态的视觉形态就是「一个被按下的按钮」，物理隐喻自带「可再按」 |
| 3 | **hover 已选中柱时，tooltip 追加一行** `再次点击取消选择` | hover | 定向补 cue |
| 4 | **`aria-pressed`** | 屏幕阅读器 | 无障碍等价通路 |

> **不做的方案**：❌「在 tooltip 里写提示」—— tooltip 只在指针已经在柱上时出现，而用户的问题恰恰是「要不要点」。❌「加一个『取消』按钮」—— 引入了一个与柱争夺注意力的控件，且和「点柱」形成两套入口。

#### 2.6.4 Tooltip 内容（**4 行，不是 6 行**）

```
┌──────────────────────────────┐
│ 2026-08              [已发出] │   ← 月份 13px/500 + BillStatusTag
│ ▪ 交付计费            312.4  │   ← 8px 色点 + 名称 12px + 金额 12px tabular
│ ▪ 运维计费            508.1  │   ← 色点用 meterCommitted
│ 合计应收              820.5  │   ← 分隔线以上，13px/500
└──────────────────────────────┘
```

- 宽度固定 **240px**，金额全部右对齐 + `tabular-nums`。
- 交付 / 运维两行各带 8px 色点（`brand` / `meterCommitted`）→ **颜色之外还有文字标签**，满足 §4.5。
- **不包含**「其中：年度新增 / 变更」两行 —— 见 §0.2 冲突裁决。

#### 2.6.5 键盘可达性（现状有 3 处缺陷，逐条修）

| 项 | 现状 | v1.4 |
|---|---|---|
| `Space` 键 | **只处理 `Enter`**（`BillingModule.jsx:89`）→ 违反 WCAG 2.1.1 | `Enter` 与 `Space` 都触发；`Space` 必须 `e.preventDefault()` 防页面滚动 |

**aria 契约**：

| 元素 | role | aria |
|---|---|---|
| 图表容器 | `role="group"` | `aria-label="全年费用趋势，12 个月，可点击柱查看单月账单；当前为累计视图"` |

**颜色不能是唯一信息载体 —— 第二重区分手段（明确回答）**：

| 信息 | 颜色 | **第二重手段** |
|---|---|---|
| 交付 vs 运维 | brand vs `#7FA8CC` | **段序恒定**（下=交付 / 上=运维，永不互换）+ 图例文字「下段 交付计费 / 上段 运维计费」+ tooltip 文字标签。三重冗余 |

| 已选 / 未选 | 满色 vs 0.42 | **标记条的有无** + 月份标签字号（12px vs 11px）与字重（500 vs 400） |

> **未采用的方案及理由**：❌ 斜向纹理（`repeating-linear-gradient`）区分两段 —— 运维段在 2–8px 的细柱上纹理会摩尔纹糊成一片灰；❌ 在柱内写数值 —— 柱宽 24px 放不下 5 位数字，且与指标卡/列表列三重重复（DESIGN §4.4）。

#### 2.6.6 累计态的视觉锚点（决策 ③ 的完整展开）

「累计」在视觉上必须能被**一眼认出**，且这个认出不能依赖 hover。三层：

1. **常驻徽标**（BlockTitle 右侧第一个元素，优先于图例）：
   `● 累计 · 截至 2026-08`，底 `filterChipBg`、点 `filterDot`、12px `brand`。
   *与 FilterBar 的「已筛选 N 项」胶囊同构* —— 全站「当前口径」的视觉语言统一。
   单月态时徽标换成 `● 2026-08 单月`，形态完全一致 → **两态在同一个位置互斥，切换时不会「徽标消失」而让用户以为出了 bug**。
2. **选中标记条缺席**：累计态下**没有任何柱带标记条**。这是「未选中任何柱」与「漏渲染」的可区分点。
3. **待出账月份的空心点 + 图例说明**：图例文字写全 `▪ 交付计费　▪ 运维计费　○ 待出账（不计入累计）`。累计口径 = `data.months.filter(m => billStateOf(data, m) !== 'DRAFT')`，因此 2026-09 有金额但**不计入**累计；不写清楚会引发「为什么 9 月有柱但合计里没有」的数据可信度危机。

#### 3.1.1 被否决的候选列（记录否决理由，防止后续误加）

| 候选 | 否决理由 |
|---|---|
| 「其中：新增需求」/「其中：变更增减」 | 已锁定决策 ⑤：**列表列也删掉** |
| 「账单状态」 | **月份级属性**，单月态下 6 行完全相同 = 常量列 = 噪音；累计态下所有部门「最后出账月」相同（mock 中 8 个系统对 6 个部门均有月度运维费）仍是常量。状态由**趋势图状态点 + 月份下拉选项文案**承载 |
| 「占 Digital 费用比重」 | **同一标量说两遍** —— 该行金额与「该行 / 全列之和」是同一份数据的绝对/相对两种表达，DESIGN §4.4-1 要求一区一主数字 |

### 3.2 月份下拉

**结论：不复用 `FilterBar`。** 四条理由：

1. `FilterBar` 的容器是 `filterBarBg` 底 + 1px 描边 + 12 padding 的**通栏横条**，为 5–7 个控件设计。放 1 个控件会得到一个 40px 高的空框，且它的视觉重量会盖过楼层 1 —— 违反「不能抢楼层一的戏」。
2. `FilterBar` 的状态区固定输出「已筛选 N 项 / 共 N 条 / 重置」三段。本控件的「清空」语义是**模式切换**（切回累计口径），不是「重置筛选条件」—— 用「重置」这个词会误导。
3. `FilterBar.isDefault`（`common.jsx:363-364`）把 `'all'` 判为默认值，一旦清空就无法显示「当前处于累计态」—— 而累计态是**默认态**，必须显式可见。
4. `FilterBar` 没有「口径胶囊」的位置，而累计/单月的口径锚点必须常驻。

**控件规格**：

```
BlockTitle extra 区：[标签 12px t3「月份」] [Select size=small width=180] [12px t2「共 6 个部门」]
```

| 项 | 规格 | 理由 |
|---|---|---|
| 组件 | antd `Select`（**裸用，不套 FilterBar**） | |
| 宽度 | 180px | 选项最长 `2026-09 · 待出账` ≈ 132px + 箭头 + padding |
| 尺寸 | `size="small"` | 高 24px，与 BlockTitle（21px）同一带，不越层 |
| `allowClear` | **❌ 不开** | 清空 = 回到累计 = 默认态。placeholder 在 allowClear 下会被清空态吞掉，用户看不到当前口径。改用**显式首项** `{value:'__CUM__', label:'全部月份 · 累计'}` 且**默认选中** |
| 选项顺序 | 首项 `全部月份 · 累计`，其后**按月份倒序**（`2026-09 → 2026-01`） | 倒序 = 「最近的在最上」，与现状月份 chip 的时间序一致 |
| 选项文案 | `2026-09 · 待出账`（`billStateOf` 三态） | 状态下拉的唯一载体（列表无状态列） |
| 前置标签 | 12px `t3` 「月份」 | 让它**看起来是个筛选器**，而不是一个值 |
| 右侧计数 | 12px `t2` `tabular-nums` 「共 6 个部门」 | 替代 `FilterBar` 的「共 N 条」，与表格行数同源 |
| `showSearch` | `false` | 9–12 个选项，搜索收益低于视觉噪声 |
| `data-testid` | `billing-month-select` | 替代已被删除的月份 chip 定位（`smoke.cjs:1057`） |

**双向联动契约**：

```
用户点柱 m        → setPicked(m)，若当前已是 m 则 setPicked(null)
用户在 Select 选 m → setPicked(m)；选「全部月份 · 累计」→ setPicked(null)
setPicked 变化     → ① 3 张指标卡重算 ② 列表切态 ③ 趋势图 active 柱切换
                     ④ 表格标题 / 标题下说明文案切换
```

> **不需要「清空」按钮**：「全部月份 · 累计」是下拉的**第一项且默认选中**，从单月态回到累计态 = 选第一项，一步可达且路径可见（比一个需要 hover 才出现的 × 更好）。

### 3.3 合计行口径（引用 v1.2 方法论，**不重造**）

`docs/v1.2-annual-table-total-column.md` §3 的核心方法论是「**合计与页头指标卡同源**」。本轮把它收紧一档：

| 态 | 合计行取值 | 视图内是否累加 |
|---|---|---|
| 单月态 | `derived.monthMap[pickedMonth].{delivery, ops, total}` | **否** —— 直接读 store 派生 |
| 累计态 | `derived.cumTotals.{delivery, ops, total}` | **否** |

**硬约束（三条同时成立才算合规）**：

1. **视图内禁止 `rows.reduce(...)`**。现状 `monthAgg`（`BillingModule.jsx:188-195`）是视图内累加，依赖「先筛选后累加」的隐式顺序 —— 一旦加入任何筛选，指标卡与合计行会同时算错。改为 store 派生。
2. **合计行 = 3 张指标卡的同源值**。同一个 `derived.*` 对象同时喂给指标卡和 `Table.Summary`，因此「指标卡说 820.5、合计行说 820.5」是**结构上必然**，不靠人工核对。
3. **「可见集合 = 全量行」是本设计的前提**。当前 6 行全部可见、无分页、无搜索、无部门筛选 ⇒ `derived` 的全量聚合 ≡ 列内可见值之和。**一旦将来加回任何筛选或分页，`derived` 必须改为对可见 `rows` 求和**，否则合计行会撒谎。此约束必须写进实现文件头注释（PROJECT 的既有做法，见 `ProjectBudgetPage.jsx:18`）。

**`derived` 需新增的字段**（追加，不改既有）：

| 字段 | 值 | 备注 |
|---|---|---|
| `cumMonths` | `data.months.filter(m => billStateOf(data, m) !== 'DRAFT')` | mock 下 = `2026-01 … 2026-08`（8 个月） |
| `cumTotals` | `{ delivery, ops, total }` = `cumMonths` 的 `monthRows` Σ | 口径 = **不含待出账月** |

```js
  window.location.replace(`#/${seg}/${MODULE_DEFAULT_VIEW[seg]}`);   // → #/billing/monthly
}
```

若 `bill` **未**加入 `MODULE_VIEWS.billing`，访问 `#/billing/bill/D-CRM/2026-08` 会在挂载的同一帧被 `location.replace` 成 `#/billing/monthly`，**详情页一闪即逝，用户完全无法察觉发生了什么**。

> **规避方案（必做）**：把 `{ key: 'bill', label: '业务部门账单详情' }` 加入 `MODULE_VIEWS.billing`。加进去之后 `sub='bill'` 命中白名单，`noOrInvalidView` 为 `false`，不重定向。**同时它还带来一个额外好处**：`activeView.label` 变成「业务部门账单详情」，`content-locator`（`App.jsx:331`）自动显示正确的面包屑。

**风险 B（显示错乱）：`content-locator` 的 `tail` 被硬编码为「新版本」**

`App.jsx:338-343`：
```jsx
{tail ? (<><span style={{color: c.t4}}>›</span><span style={{color: c.brand}}>新版本</span></>) : null}
```

本路由的 `tail` 是 `2026-08`，会被显示成 **「› 新版本」**。

> **规避方案**：把 tail 标签改为**按板块取**：`const TAIL_LABEL = { budget: '新版本', billing: null }`；`TAIL_LABEL[seg]` 为 `null` 时直接渲染 `tail` 原值（月份），否则渲染映射文案。改动 3 行，不影响 `budget/project` 的现有显示。

**风险 C（既存缺陷，本轮顺手修）：`MODULE_VIEWS[seg]` 空指针**

`App.jsx:186` 的 `MODULE_VIEWS[seg].some(...)` 在**该行无条件执行**。若 `seg` 不在 `MODULE_VIEWS` 的键里（`#/home/xxx`、`#/garbage/xxx` —— `SEG='home'` 虽被 `LEGACY_SEGS` 收录但**不在 `MODULE_VIEWS`**），`MODULE_VIEWS[seg]` 为 `undefined` → **TypeError → 白屏**。`isValidModule` 的短路保护写在 `&&` 的**左侧**，救不了这一行。

> **规避方案**：`const list = MODULE_VIEWS[seg] || [];` 再 `!list.some(...)`。2 行，消除白屏。

**风险 D：`drillTargetOf` 元组长度变化会静默丢参**

`traceNodes.js:190` 现返回 3 元组 `['billing','monthly', ctx.billId]`；两个调用点都以 `onNavigate(t[0], t[1], t[2])` 传参（`BillingModule.jsx:640`、`BillingModule.jsx:1181`）。若改为 `['billing','bill', deptCode, month]`（4 元组）而**只改返回不改调用点**，第 4 段月份会被 `go()` 的 `if (tail)` 静默丢弃 → 落在 `#/billing/bill/D-CRM`（无月份）→ 详情页走「非法参数兜底」白屏式空页。

## 7. v1.4.1 修订（用户 2026-10-03 追加要求）

### 7.1 趋势图从合并楼层移出，独立成楼层

用户要求：「柱状趋势图还是单独一个楼层吧，但放在列表板块中」。

**理由（推翻 design §0.1 ⑤）**：原「并列」决策的依据是「点了柱要能看到指标联动」。
但移除全部筛选项后，指标卡已不承载任何交互，其数值由列表合计行同源给出；
而趋势图服务的是「**列表看的是哪一段时间**」—— 它必须紧贴列表、位于其上方。
由并列改为主动下移后，「指标 = 总量 / 趋势 = 期间 / 列表 = 明细」三层递进关系更清晰；
并列会让两个职责不同的楼层挤在同一视觉层里。

**指标卡随之改横向一行**（原纵向轨是为并列时压缩高度而设，独立成楼层后已无必要）。

- 折线取「月度合计」而非「累计」或「环比增长率」。堆叠柱的总额需心算相加才能得到，

- 未取「累计」：与柱的「当月值」量纲不同，同图易被误读为「当月变高了」，需双轴。

「楼层三 = 部门汇总」在「楼层四/五 = 逐项明细」之前，是**先汇总后展开**的顺序；
但若按费用类型顺序，交付/运维应紧跟趋势图。用户选了前者 ——
因为楼层三承担「点行进详情」的入口，是明细的索引层，放中间更顺。

### 8.2 关键口径：业务量化价值取自「上线后复盘」，不是 BRD 预估

**用户原话（口径纠正，勿回退）**：

> 这里是账单，账单是已上线项目的收费，因此，这里的业务价值，不应该是 BRD 里面的金额，
> 而是业务在上线后，完成复盘，填入复盘文档的同时，写入或从复盘文档里面抽取的真实的业务增量价值信息

**背景事实**：`DEMANDS[].bizValueAmount`（BRD 预估口径）**只存在于 FY2027**，
FY2026 全部缺失（`mock.js:436` 原有注释已写明「FY2026 未给出该字段 → null，按「—」处理」）。
若沿用它，交付楼层的 ROI 会**整列显「—」**，楼层失去意义。

**处置**：在 `mock.js` 新增 `RETRO_RECORDS`（9 条 = 会计入交付计费的全集），
挂 `retroDoc` / `realizedValue` / `retrofitDone` / `retroSummary` 四个字段。

**术语纪律（写入代码注释，不可混用）**：

| 字段 | 口径 | 用在哪 |
|---|---|---|
| `DEMANDS[].bizValueAmount` | BRD 立项**预估** | 《项目预算计划》的预估 ROI |
| `BRDS[].realizedValue` | 上线后复盘**实际**增量价值 | **账单楼层的 ROI** |

两者是**不同事实源**，页面上不得用同一个字段。ROI = `realizedValue / 账单行金额`；
分子为 null 或分母 0 ⇒ 返 `null`（页面显「—」），**绝不返 0**（会读成「没有回报」）。

其中 2 个项目（BRD-2026-0112 / 0118）故意设为未复盘（`retrofitDone: false`），
上线月 2026-09 超出累计边界 ⇒ **只在单月态可见**，正好覆盖「待复盘」显示分支。

### 8.3 行粒度决策

**交付楼层：行 = 一条交付计费行**（= `buildBill().lines[type='DELIVERY']`）。
同一 BRD 只在交付上线月出账一次，故累计态下每个项目只出现一行，不存在跨月重复计数。

**运维楼层：行 = 一个系统**（不按「系统 × 部门」展开）。
理由：运维是「系统级计费程序 → 按 BU 分摊」，用户要回答的是
「这个系统这区间一共收了多少、摊给了谁」—— 金额要聚合，分摊 BU 单列成清单。

### 8.4 两条易错口径

1. **交付楼层的「digital 费用」= 账单行金额**（`buildBill().lines[].amount`，
   即评估价 + 已批准变更），**不是 `evalAmount`**。有 CR 时两者不相等，
   用错会导致「楼层合计 ≠ 部门账单合计」。
2. **固定年费类系统的用量必须显「固定年费 / 月」而非 0** ——
   `buildBill` 里这类 `volume = null`，把 null 当 0 求和会得到「0 用量」的错误结论。

### 8.5 楼层视觉分隔（`FloorHead` 组件）

页面扩到 5 楼层后，原 `BlockTitle`（14px 灰黑）已无法区分楼层。新增三重视觉信号：
① 左侧 3px brand 竖条 + 16px 标题（高于 BlockTitle 的 14px）；
② `楼层 N` 胶囊徽标（序号由调用方传入，不在组件内硬编码）；
③ 标题下方通栏细线。另在每张 Card 上加 `borderTop: 3px solid` 色条做卡片级分隔。

### 8.6 列宽取舍（显式，非核算失误）

|---|---|---|

### 8.8 本轮踩到的两个 jsdom 交互坑

1. **antd `Select` 在 jsdom 下需 `mousedown` 才展开下拉**，用 `click()` 无效。
2. **`allowClear` 的清除图标同样监听 `mousedown`** —— 图标存在、点击后值不变，
   极易误判为「清空功能坏了」。**凡操作 antd Select，一律用 `mousedown`。**
3. `goView()` 只改 hash、**不重置组件 state** —— 测完切月后必须显式清空月份，
   否则后续断言继承了上一个月的口径（表现为「点行跳错账单」这类诡异失败）。

### 9.7 本轮新增的三个测试坑（都实测踩过）

1. **React 会把 `borderLeft: '4px solid X'` 规范化为单条 `border-width: 1px 1px 1px 4px`**，

   ⇒ 断言样式必须直接读 `style` 里的 `border-width` 字符串并按段取。
2. **「同组件不同参数」的断言必须显式切换上下文**：

   必须先 `goView('billing/monthly')` 再断言，再切回。
3. **`python -c` 里的正则替换常因 CRLF / 转义而不命中**，改文件优先用 Edit 工具；
   必须核对替换是否真的生效（打印 `mutated: True/False`），否则会误以为已改。
