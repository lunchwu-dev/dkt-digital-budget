# v0.9 《年度 BP 计划》独立页面 · 需求描述与设计说明

> 本文件是**需求描述文档（Design Brief）**，不是实现文档。目的：把用户口述的 4 点需求形式化，逐条判定「理解准确 / 需修正 / 需澄清」，收敛歧义，输出可直接交给研发的需求基线。
> 本轮**只产出文档，不改任何源码**。文中所有"现状"均以当前代码为准（行号取自 `src/pages/BudgetModule.jsx`、`src/store.jsx`、`src/domain/calc.js`、`src/App.jsx`、`src/data/mock.js`），与代码不符处以代码为准。
> 上一轮 v0.8 处理的是「② 项目预算」的页面化；本轮处理「① 年度 BP」。两者是同一主表的两个下钻兄弟，形态应统一，但**状态机不可照搬**（见 §6.1）。

---

## 结论前置（6 条最关键的判断）

1. **页面作用域 = 「一个部门 × 一个编制年」**（`PLAN_FY = 2027`）。用户原文"应以独立页面形式拉起**该项目**《年度 BP 计划》"中"该项目"与其后 4 点描述不自洽（4 点全部按"部门内多个版本"描述），判定为沿用上一轮的笔误，作**部门级**解释。此点仍列入 §9-Q1 待确认，因为它是唯一会推翻整页结构的分歧。
2. **最重要的修正：BP 的内容字段必须从 `BP_RECORDS` 下移到 `BP_VERSIONS`，每个版本存一份完整快照。** 现状 `BP_VERSIONS` 只有 4 个字段（`version / at / owner / changeNote`，`mock.js` 164–174 行），**没有**名称、量化目标、摘要、文档链接——"每行一个版本"在当前模型下**无法渲染**。这是本轮唯一的模型级阻断项。
3. **不允许两处并存为真相源。** 内容字段下移后，`BP_RECORDS` 不得继续独立保存 `version / docRef / changeNote`——否则主表列与页面列表迟早分叉（与"合计行必须与列内同源"是同一类问题）。**建议 `BP_RECORDS` 退化为派生投影，前端一律不直接读 `data.bpRecords`**（§5.3）。
4. **不新增任何状态。** v0.5 定稿的"BP 只有 `已提交 / 未提交`"继续成立：用户第 4 点"提交后即更新对应业务 BP"= **无草稿态、无复核态、无归档态**。这一点与 v0.8 正好相反（项目预算页因流程含"业务复核确认"而必须新增草稿与复核态）。**不要把 v0.8 的状态机复制到本页**（§6.1）。
5. **AI 摘要是本轮的隐藏风险点**：生成结果必须**落库为版本快照**，否则同一版本在不同时间/不同次渲染会看到不同摘要，"版本记录"失去稳定性。相应地，摘要列是全表**唯一允许后置写入**的字段（`pending → 终态`，且仅此一次），其余字段一律不可变（§7）。
6. **两个实现约束必须点名**：① 新路由 key **不能叫 `bp`**——它已被 `LEGACY_VIEWS.budget.bp` 占用（`App.jsx` 62 行），且 `tests/smoke.cjs` 820–822 行明确断言 `#/budget/bp` 必须重定向到 `annual`；② `store.planAction` 当前签名只接 `note`（`store.jsx` 79 行），新浮层要落 5 个字段，**必须先扩签名，否则字段静默丢失**（§8.4、§10）。

## 一、需求理解确认

逐条复述用户原文，并给出判定。

### 第 1 点：独立页面取代右侧浮层

> 原文：在年度预算页面中，点击某业务部门的年度BP后，应以独立页面形式拉起该项目《年度BP计划》，而不再使用右侧浮层。

**判定：方向准确；指代需确认 1 处。**

| # | 用户表述 | 判定 | 说明 |
|---|---|---|---|
| 1.1 | 入口在《年度预算计划》主表 | **准确** | 现状：主表「① 年度 BP」列的 `PlanCell` 点击 → `setCtx({stage:'BP'})` → 打开右侧 Drawer（`BudgetModule.jsx` 411–430 行打开、636–688 行抽屉、665 行 BP 分支） |
| 1.2 | 改为独立页面 | **准确** | 获得 URL、可刷新、可分享、可后退。与 v0.8「② 项目预算」页面化的做法一致（§2） |
| 1.3 | "该项目"的指代 | **需确认** | 若 = **单条 BP 文档**，则页面只有一条记录，"每行一个版本"无从展开；若 = **该部门的年度 BP**（推荐），则页面 = 该部门全部版本。按推荐解释推进，§9-Q1 待拍板 |
| 1.4 | "不再使用右侧浮层" | **准确** | 需连带处理：抽屉 BP 分支移除；且**综合视图（SUMMARY）抽屉里的「① 年度 BP 文档」卡片**（`BudgetModule.jsx` 663、716–722 行）当前点开也是 BP 抽屉，必须一并改为跳页面——否则同一个浮层从另一个入口仍能打开 |

### 第 2 点：列表每行代表一个版本

> 原文：《年度BP计划》页面主体为一个列表。列表每一行代表一个版本的年度BP计划。

**判定：结构准确，但与现状是"主体反转"，且被数据模型阻断。**

| # | 冲突/缺口 | 说明 | 处理方向 |
|---|---|---|---|
| 2.1 | 页面主体反转 | 现状 BP 浮层的**主体是"当前版本"**（`Descriptions`，`BudgetModule.jsx` 802–815 行），版本记录表只是附属（829–855 行）。新需求要求**主体是版本列表**，当前版本不再是独立展示块 | 版本列表升为主体；"当前版本"改为在列表内标识（§3.3） |
| 2.2 | **数据模型阻断** | `BP_VERSIONS` 只有 `version / at / owner / changeNote`，无名称 / 量化目标 / 摘要 / 文档链接；`BP_RECORDS` 才存 `docKind / docRef / docCount`，但**只存当前版本一份** | 内容字段下移到版本记录（§5） |
| 2.3 | 版本不可变 | "每行一个版本"隐含：已提交版本的内容**不可再编辑**。更新 = 追加一个新版本行，不是修改旧行 | 全表只读、无行内编辑；唯一例外是 AI 摘要有一次后置写入（§7.4） |

### 第 3 点：列表 5 列

> 原文：每行包含以下列：BP名称、年度业务量化目标、BP内容核心摘要（由业务填写，未填写则由AI自动生成）、BP文档链接、该版本修订说明。

**判定：5 列中 4 列需新增字段、1 列口径待定、且缺 1 列必需信息。**

| 用户字段 | 现有模型映射 | 判定 |
|---|---|---|
| BP 名称 | **不存在**（BP 只有 `docRef` 文件名，如 `FY2027 电商数字化规划.pdf`） | 需新增字段 `name` |
| 年度业务量化目标 | **不存在** | 需新增字段 `goals`；**量纲未定**（§4.2 / §9-Q2）|
| BP 内容核心摘要 | **不存在** | 需新增字段 `summary` + `summarySource`（业务填写 / AI 生成；§7） |
| BP 文档链接 | `BP_RECORDS.docKind`（`link`/`file`）+ `docRef` + `docCount` | 口径需收窄：现状支持"文档链接**或** N 份附件"，用户只写"链接"（§4.3 / §9-Q4） |
| 该版本修订说明 | `BP_VERSIONS.changeNote` | **准确**，已有字段可直接用 |

- **必须新增的第 6 列「版本」**：用户未列，但"每行代表一个版本"必须能让人认出**是哪一版、什么时候提交的**。现状可用的只有 `version` 与 `at`，若都不出现，列表退化为若干行无法区分的文本。建议：**版本号 + 提交时间合并为首列**（而非拆两列），理由见 §4.1。
- **不需要「操作」列**：文档链接列自带外链动作；版本不可变，无行内操作。加"操作"列是空跑。

### 第 4 点：「更新年度 BP」入口 + 浮层

> 原文：提供"更新年度BP"入口，点击后弹出浮层，由业务在浮层中完成上述信息的填写与更新，提交后即更新对应业务BP。

**判定：准确；需修正 2 处、澄清 2 处。**

| # | 冲突/缺口 | 说明 | 处理方向 |
|---|---|---|---|
| 4.1 | 与现有浮层冲突（双入口风险） | 现状主表「操作」列的"下一步"按钮也会对 BP 打开 `PlanActionModal`（`BudgetModule.jsx` 332–345 行 `openAction` → 691–707 行；表单只有 1 个"变更说明"字段，1292–1333 行）。新浮层若独立新增而不回收旧入口，会出现**两个入口两套表单**做同一件事 | **收敛为一个浮层**，主表动作同步切到新浮层（§8.3） |
| 4.2 | "提交后即更新"= 无草稿 | 与 v0.8 的项目预算页不同，BP 不需要草稿态。但同时意味着：**浮层填写一半关闭 = 内容丢失**，无暂存 | 采用"提交即生效"，不做草稿；须在 §9-Q3 向业务确认可接受 |
| 4.3 | 「更新」与「首次提交」是同一入口还是两个 | 现状 `ACTION_META['BP_提交']` 只有一条文案"提交 / 更新年度 BP"（`BudgetModule.jsx` 111–118 行），按钮文案按有无 `bp` 切换（821–823 行） | **同一入口，文案与标题按有无历史版本切换**（§8.2），避免两个按钮 |
| 4.4 | 提交角色未指定 | v0.5 口径：BP 由业务部门提交，Digital 只读 | **沿用**：仅业务部门可提交；Digital 进入为只读（§9-Q9 复核） |

## 二、页面定位与入口变更

### 2.1 从浮层到独立页面

现状：主表「① 年度 BP」格 → `setCtx({stage:'BP', dept})` → 右侧 Drawer 渲染 `BpPanel`。
目标：改为独立页面，获得 URL。

| 项 | 方案 |
|---|---|
| 路由 key | 新增 `bpplan`（**不可用 `bp`**，见结论前置 6） |
| 路径 | **`#/budget/bpplan/{deptCode}`**，如 `#/budget/bpplan/D-RETAIL` |
| 注册位置 | `App.jsx` `MODULE_VIEWS.budget` 增 `{key:'bpplan', label:'年度 BP 计划'}` |
| 为什么必须注册 | 未注册时 `App.jsx` 168–175 行的归一 effect 会把 `#/budget/bpplan/D-RETAIL` 直接 `replace` 成 `#/budget/annual`，页面根本进不去 |
| key 命名禁用清单 | `pool / bp / demand / plan / deptpool`（`App.jsx` 59–67 行旧视图重定向） ∪ `annual / consume`（现行视图） |
| `MODULE_DEFAULT_VIEW` | **不改**（仍为 `annual`） |
| SiderNav | **不改**。`SiderNav` 用硬编码 `GROUPS`（`SiderNav.jsx` 15–49 行），与 `MODULE_VIEWS` 解耦，新增 view 不会进左导航——这正是下钻页应有的表现 |
| 面包屑 | **自动生效**，复用 `App.jsx` 289–311 行定位条，显示「预算管理 · 编制与消耗 › 年度 BP 计划 › D-RETAIL」 |
| 编制年 | 必须用 `PLAN_FY = 2027`（`BudgetModule.jsx` 70 行），**不可用 `globalFy`**。理由同 v0.8：年度预算计划恒为次年编制口径，而 `globalFy` 可切到 2026 执行年，会造成"点进去看到另一年份 BP"的错位 |

### 2.2 进入 / 退出路径

| 方向 | 路径 |
|---|---|
| 进入①（主入口） | 《年度预算计划》主表 → 部门行「① 年度 BP」格 → `#/budget/bpplan/{deptCode}` |
| 进入②（综合视图） | SUMMARY 抽屉「① 年度 BP 文档」卡片 → 同 URL（**须改，见 §1 第 1.4 项**） |
| 进入③ 全局搜索 | **本轮不加入口**。BP 记录 id 形如 `BP-2027-RETAIL` 非搜索前缀，`onGlobalSearch` 只识别 `DM- / BRD- / CR- / BILL-`（`App.jsx` 198–215 行）。扩展前缀属独立需求，见 §9-Q8 |
| 退出 | 页头「返回年度预算计划」→ `#/budget/annual`；浏览器后退同样有效 |

### 2.3 深链与查询参数

`#/budget/bpplan/D-RETAIL` 天然可分享、可刷新。**不需要** `?ver=` 之类的查询参数——因为本页无"进行中版本"概念（无草稿/无复核），列表恒为完整历史。
⚠️ 附带说明：`useHashRoute` 只解析三段并**丢弃 `?` 之后的内容**（`App.jsx` 83 行）。若未来需要 `?focus=` 定位某个版本，必须先扩展该解析器。本轮不需要。

### 2.4 与 v0.8 「② 项目预算」页的关系

两页是同一主表的两个下钻兄弟，**建议共用"下钻页壳"**（页头 + 返回按钮 + `PageHead` 版式），避免两份重复代码：

| 项 | ② 项目预算（v0.8） | ① 年度 BP（本轮） |
|---|---|---|
| 路由 key | `project` | `bpplan` |
| 列表粒度 | 一行 = 一条**项目**（需求） | 一行 = 一个**版本** |
| 是否有进行中版本 | 有（草稿 / 待 Digital 反馈 / 待业务复核） | **无** |
| 状态机 | 6 态（S0–S5） | **2 态**（未提交 / 已提交） |
| 是否需扩 `store` 的草稿能力 | 需要 | **不需要** |
| 主操作入口 | 页面按钮（随状态变） | 「更新年度 BP」单个按钮（浮层） |

> 形态统一性：本轮之后，主表三种下钻里 **BP + 项目预算 = 独立页面，仅 OPS 仍为浮层**。建议在 §9-Q7 提出 OPS 是否一并页面化，交由业务决定，不在本轮做。

## 三、页面结构规范

页面自上而下 3 个楼层。命名与现有组件对齐（`PageHead` / `Blank` / `Hint` / `Button` 取自 `components/common.jsx`）。

### 3.1 楼层 0 · 页头（PageHead）

- 标题：`{部门名} · 年度 BP 计划`
- 副说明（一句话口径）：`BP 以"一次提交 = 一个版本"记录；列表为历史版本，最新版本在下发即生效，历史版本只读。`
- `extra`：
  - **返回按钮**（`ArrowLeftOutlined`，`type="text"`）→ `#/budget/annual`
  - **主操作按钮**「更新年度 BP」（`type="primary"`，`FileTextOutlined`）→ 打开浮层（§8）
- 责任人信息行（12px，`t3`）：`业务责任人 {bpOwner} · Digital 对接人 {digitalOwner}`
- `data-testid="budget-bp-plan-page"`

### 3.2 楼层 1 · 列表标题行（不占独立楼层）

**不加概览卡片楼层。** 理由：用户明确"页面主体为一个列表"，加一排 `Metric` 卡会把列表推下首屏，与"主体是列表"的要求相悖（v0.8 项目预算页有概览楼层，是因为那一页用户明确要了"当前版本 + 项目总费用"；本轮没有此要求，不做）。

改为在列表标题行右侧放一行极简统计（12px，`t3`）：

`共 {n} 个版本 · 当前 {V2.1} · 最近更新 {2026-09-22 10:12}`

- 组件：`BlockTitle` + `extra`（`common.jsx` 297 行）
- 数据来源：`bpVersions.length` / `bpVersions[0]`（**派生自版本列表，不读 `BP_RECORDS`**）

### 3.3 楼层 2 · 主体：版本列表

- 容器 `data-testid="budget-bp-table"`（**建议由 `budget-bp-versions` 更名**，语义与页面主体一致）
- 列定义见 §4
- 整表**默认只读，无行内编辑**（版本不可变，§1 第 2.3 项）
- 排序：**提交时间倒序**，最新版本固定首行
- **"当前版本"的标识方式（关键取舍）**：在首列「版本」内用**文字自身着色 + 字重**表达——当前版本 = 品牌色 `c.brand` + 500 字重，历史版本 = `c.t3` 灰。**不新增"当前/历史"列、不加色条、不用 `Tag`**。
  > 理由：版本号本身就是那个标量，"当前"只是它的一个档位；为此另加一列或一条彩条 = 同一信息说两遍，且 `Tag` 有底色与边框，视觉重量会压过版本号本身。这与现有 `PlanCell` 的"圆点承载状态、不抢焦点"设计哲学一致（`BudgetModule.jsx` 153–231 行注释）。
- 合计行：**不需要**。版本之间不是可加总的关系（不像项目费用可求和）；加"合计"会误导。
- 空态：`Blank`，文案「该部门 FY2027 年度 BP 尚未提交 · 点击右上角「更新年度 BP」提交首版」
- 行高控制：`size="small"`；摘要列 2 行截断、修订说明列 1 行截断（§4.4）

## 四、列表列规范

### 4.1 列定义与宽度预算

内容区可用宽度（1440 视口、Sider 展开）：`1440 − 224 (sider) − 48 (padding) = 1168`。

| # | 列 | 类型 | 取值 / 枚举 | 数据来源 | 可编辑 | 空态 | 建议宽度 / 对齐 |
|---|---|---|---|---|---|---|---|
| 1 | **版本** | — | 主行 `V1.0 / V1.1 …`；次行 `2026-09-22 · 陈昊` | `BP_VERSIONS.version` + `at` + `owner` | 否 | —（恒有） | **132** / 左 |
| 2 | BP 名称 | string | 1–60 字 | **新增 `name`** | 否 | `—` | 200 / 左，`ellipsis` + `title` |
| 3 | 年度业务量化目标 | **待定**（§4.2） | 待定 | **新增 `goals`** | 否 | `—` | 200 / 左 |
| 4 | BP 内容核心摘要 | string（长文本，建议 ≤300 字） | 自由文本或 AI 生成 | **新增 `summary`** + `summarySource` | 否 | 见 §7.5 | 280（`flex`）/ 左，**2 行截断** |
| 5 | BP 文档链接 | `[{name, url, kind}]` 或 `null` | `kind ∈ {link, file}` | **新增 `docs`**（由 `BP_RECORDS.docKind/docRef/docCount` 迁入） | 否 | 「未提供文档」灰字 | 140 / 左 |
| 6 | 该版本修订说明 | string | 自由文本 | `BP_VERSIONS.changeNote`（**已有**） | 否 | `—` | 200 / 左，**1 行截断** |

宽度合计 = `132+200+200+280+140+200 = 1152` ≤ 1168 ✅（窄屏由 `scroll={{ x: 1152 }}` 兜住）。

**为什么"版本号 + 提交时间"合并为一列而非拆两列**：
- 二者共同回答同一个问题——"这是哪一版、什么时候的"；拆开后每行都需要读两格才能定位，扫描成本翻倍。
- 若拆成独立两列，宽度预算会超（`+96+150`），必须牺牲摘要列宽——而摘要正是本页信息量最大的列。
- 形态与 `PlanCell` 的两级结构一致（主值 + 12px 次要行），视觉语言统一。

### 4.2 「年度业务量化目标」量纲（待定，本页最大不确定项）

"量化目标"字面暗示数值，但跨部门**不可能统一量纲**：门店看 GMV / 坪效 / 开店数，电商业看 GMV / 转化率 / 直播时长，供应链看履约时效 / 供应商协同覆盖。因此：

| 候选 | 形态 | 优点 | 代价 |
|---|---|---|---|
| **A（推荐）结构化文本** | 多行文本，约定每行一条 `指标：目标值（口径）`，如 `GMV：同比 +18%`、`直播中台：Q3 上线，覆盖 12 场/月` | 零建模成本、跨部门通用、可读性最好 | 无法做横向汇总/校验；排版依赖业务自觉 |
| B 结构化数组 | `[{ metric, target, unit }]` | 可排序、可校验、未来可汇总 | 跨部门指标名不统一，汇总仍无意义；浮层需要动态增删行的复杂交互 |
| C 纯数值 | number + 单位 | 最"量化" | 单指标装不下多目标，且各部门不同质，必然被业务要求改回文本 |

**推荐 A**，理由：本页是**版本记录**（追溯用途），不是指标看板；结构化收益（汇总）在跨部门异构指标上不成立，而建模与交互成本是实打实的。本项须由业务拍板（§9-Q2），**量纲不定则列宽、浮层控件、mock 数据全部无法定稿**。

### 4.3 「BP 文档链接」口径收窄

现状支持两种形态（`BP_RECORDS.docKind`：`link` = 单个外链，`file` = N 份附件），浮层里以 `docRef` + `docCount` 表达（`BudgetModule.jsx` 806–809 行）。

| 候选 | 说明 |
|---|---|
| **A（推荐）保留多文档** | `docs: [{name, url, kind}]`，列内显示**主文档链接**，其余折叠为 `+N`；悬停 `title` 列出全部 |
| B 只允许 1 个链接 | 严格贴合用户字面 | 
| C 只允许上传附件 | 与现状 `link` 形态冲突 |

**推荐 A**，理由：① 现状数据模型已支持多文档（`docCount` 最大到 4），收窄为单条会造成**存量数据丢失**；② "链接"与"附件"是同一语义的两种载体，强行只留一种属于无收益的破坏性变更；③ 列宽 140 只够放主链接，用 `+N` 折叠即可不侵占摘要列。

### 4.4 长文本列的行高控制

摘要与修订说明两列都是长文本，若全量展开，单行可达 8–10 行，一屏仅显示 1–2 个版本 —— 直接违背"列表"的信息密度诉求。

| 列 | 截断 | 手段 |
|---|---|---|
| 摘要 | **2 行** | antd Table `column.ellipsis:{showTitle:false}` + `Typography.Paragraph ellipsis={{rows:2, tooltip}}` |
| 修订说明 | **1 行** | `ellipsis: true`（列宽 200 时约 13 个汉字） |

> 与 v0.6/v0.6.1 的密度治理同源：先定"一行最多显示多少信息"，再定内容承载方式，而不是反过来。

## 五、数据模型修订（本轮核心）

### 5.1 现状盘点

| 数据源 | 字段 | 问题 |

### 5.3 `BP_RECORDS` 的处置（**必须二选一，不可并存**）

| 候选 | 说明 | 判定 |
|---|---|---|
| **A（推荐）降级为派生投影** | `calc` 暴露 `bpOf(data, dept, fy) => bpVersionsOf(...)[0] \|\| null`；`annualPlanRow.bp` / `bpStatus` / `bpDone` 全部改为读它。`BP_RECORDS` 保留在 mock 里仅为兼容未改完的消费方，**并在文件头注释标为 deprecated** | ✅ 推荐 |

## 六、版本与提交规则

### 6.1 状态机（**刻意保持最小**）

| 状态 | 含义 | 列表可见性 | 版本号 |
|---|---|---|---|
| `未提交` | 该部门从未提交过 BP | 列表空态 | 无 |
| `已提交` | 存在至少一个版本 | 列出全部版本 | 递增 |

```
[未提交] ──业务「更新年度 BP」提交──▶ [已提交]
                                        │
                                        └── 再次提交 ──▶ 追加新版本（V1.1 → V1.2 …），旧版本保留只读
```

**与 v0.8 的关键差异（必须点名，防止错误照搬）**：

| 项 | ② 项目预算（v0.8） | ① 年度 BP（本轮） |
|---|---|---|
| 草稿态 | 新增（S2） | **无**——用户明确"提交后即更新" |
| 复核 / 确认环节 | 新增（S4，业务复核确认） | **无**——v0.5 已定稿 BP 无复核 |
| 退回落差 | 有（复核不通过退回） | **无** |
| 得号时机 | 后移到业务复核确认 | **提交即得号**（沿用 `nextMinorVersion`） |
| 进行中版本暴露 | 需"入口徽标"机制 | **不需要**——不存在进行中态 |

> 一句话：本页的复杂度**全部在数据模型与 AI 摘要**，不在状态机。任何"为了统一而给 BP 加草稿/复核"的建议都应拒绝——那会凭空制造两套生命周期。

### 6.2 提交语义

- **一次提交 = 追加一个版本**（不是覆盖）。版本号由 `C.nextMinorVersion(history)` 生成（`calc.js` 664–672 行），首个版本 `V1.0`。
- **提交即生效**：列表首行立即出现新版本；主表「① 年度 BP」列的版本号同步刷新为最新版本。
- **历史版本不可编辑、不可删除**（本轮不提供回滚，见 §9-Q6）。
- 每次提交写一条 `planActivity`（沿用 `store.planAction` 的既有留痕机制，`store.jsx` 83–95 行），`stage='BP'`、`action='提交' | '更新'`、`version=新版本号`。

## 七、AI 摘要生成规则（本轮最大技术风险）

### 7.1 触发条件

| 场景 | 行为 |
|---|---|
| 业务在浮层填写了摘要 | `summarySource='business'`，**AI 不介入、不覆盖** |
| 业务留空摘要并提交 | `summarySource='ai_pending'`，提交**立即成功**，摘要异步生成后回填 |

### 7.2 生成依据（**含一项须向业务如实说明的限制**）

理想依据 = 该版本 BP **文档正文**。但当前原型**没有文档解析能力**（`mock.js` 只有 `docRef` 字符串与 `docCount`）。因此：

| 依据 | 可行性 | 摘要质量 |
|---|---|---|
| 文档正文抽取（正式版应做） | 原型**不具备** | 高 |
| 仅依据已填字段（名称 / 量化目标 / 文档链接）改写归纳 | 原型可做 | **中**——本质是对一句话做扩写，信息增量有限 |

> **必须如实告知**：在原型阶段（无文档解析）AI 摘要的价值有限；正式版需接入文档正文抽取，否则该字段易被业务认为"没有用"。

### 7.3 异步与快照（**关键词：必须落库**）

```
业务提交（摘要留空）
   └─▶ 同步：写入版本行，summary=null, summarySource='ai_pending'   ← 提交立即成功，不阻塞
         └─▶ 异步：AI 生成
               ├─ 成功 ──▶ 回填 summary，summarySource='ai'
               └─ 失败 ──▶ summarySource='ai_failed'（格内提示可手填）
```

**为什么必须是快照而不是每次渲染实时生成**：若摘要不落库，同一版本在不同时间打开会看到不同文本，"历史版本记录"的稳定性直接失效——这与"合计必须与列内同源"属于同一类错误（同一事实有两个来源）。

### 7.4 唯一允许的后置写入

§1 第 2.3 项已定"版本不可变"。**唯一例外**：`summary` 与 `summarySource` 允许从 `ai_pending` 单向写入到 `ai` / `ai_failed`，**仅一次，且不可逆**。其余字段（名称 / 目标 / 文档 / 修订说明 / 时间 / 操作人）一旦落库即冻结。

### 7.5 摘要列的空态与来源标记

| `summarySource` | 列内展示 |
|---|---|
| `business` | 摘要正文 + 12px `t3` 后缀 `· 业务填写` |
| `ai` | 摘要正文 + 12px `t3` 后缀 `· AI 生成` |
| `ai_pending` | `AI 生成中…`（12px `t3`，可配轻量 loading 图标） |
| `ai_failed` | `AI 生成失败 · 可在「更新年度 BP」中补充`（12px `t3`） |
| `null`（老数据 / 均未填） | `—` |

> **来源标记用 12px 灰色文字，不用 `Tag`**。理由同 §3.3：来源是摘要的附属属性，`Tag` 的底色与边框会与摘要正文争夺视觉重心。这与 `PlanCell`（`BudgetModule.jsx` 223–226 行）"圆点 + 小字"的处理保持一致。

### 7.6 原型实现建议

Demo 阶段用**前端模拟**：提交后 `setTimeout(≈1.2s)` 回填模板文本，覆盖 `ai_pending → ai` 的完整视觉过程；正式版由后端异步任务承接。**不建议原型直接跳过异步**——否则"AI 生成中"这一态在验收时无法演示，而它恰恰是业务最可能追问的细节。

## 八、「更新年度 BP」浮层规范

### 8.1 组件取舍：新建专用浮层

| 候选 | 说明 | 判定 |
|---|---|---|
| **A（推荐）新建 `BpUpdateModal`** | 5 个字段 + 摘要 AI 提示 + 文档多行编辑，与 `PlanActionModal` 的单字段结构差异过大；后者还被 DEMAND / OPS 共用（`BudgetModule.jsx` 110–134 行 `ACTION_META` 六个动作共用同一个 Modal） | ✅ |
| B 扩展 `PlanActionModal` | 会让 DEMAND / OPS 被迫接受无关键位与校验逻辑，三处耦合 | ❌ |

**但必须同时做一件事**：把主表「操作」列的 BP 动作从 `PlanActionModal` **切到新浮层**（§1 第 4.1 项）。否则同一动作存在两个入口、两套表单，且旧入口不含新字段——提交后会写出字段残缺的版本行。

### 8.2 标题与文案

| 场景 | 标题 | 主按钮 |
|---|---|---|
| 该部门无历史版本 | `提交年度 BP（首版 V1.0）` | 提交 BP |
| 已有历史版本 | `更新年度 BP（将生成 V{next}）` | 提交更新 |

> 版本号在浮层内为**只读预告**，提交后由 `store` 调 `nextMinorVersion` 确定。**禁止前端硬编码或自行计算版本号**——否则与 `calc.nextMinorVersion` 分叉，出现重号或跳号（`store.jsx` 100 行已用 `version || C.nextMinorVersion(history)` 作为唯一入口）。

### 8.3 字段与校验

| 字段 | 控件 | 必填 | 校验 / 提示 |
|---|---|---|---|
| BP 名称 | `Input` | ✅ | 1–60 字 |
| 年度业务量化目标 | `Input.TextArea`（rows=3） | 待定（§9-Q2） | 提示：`每行一条，如「GMV：同比 +18%」` |
| BP 内容核心摘要 | `Input.TextArea`（rows=4） | ❌ | 留空提示：`留空将由 AI 依据本版本内容自动生成摘要` |
| BP 文档链接 | 动态列表（`Form.List`）：每行 `名称` + `URL` | ✅ 至少 1 条 | URL 格式；支持 `+ 添加` / 删除；`kind` 由是否上传附件推导 |
| 本次修订说明 | `Input.TextArea`（rows=3） | ✅ | 写入 `changeNote`；首版默认 `首次提交` |

- 浮层内使用 `Form` `validateFields`，**与 `PlanActionModal` 同样的取消/确认语义**（`cancelText="取消"`，`maskClosable` 建议 `false` 防误关，因为无草稿保护）。
- 根节点 `data-testid="budget-bp-update-modal"`。

### 8.4 提交链路（实现约束，**必须点名**）

现状 `store.planAction` 签名：

```js
planAction({ deptCode, fy, stage, action, note, version, actor, role })   // store.jsx 79 行
```

BP 分支只把它映射为 `changeNote: note`（105、124 行）。新浮层有 5 个字段，**必须扩展签名为 payload 透传**：

```js
planAction({ deptCode, fy, stage: 'BP', action: '提交', payload: { name, goals, summary, docs, changeNote }, actor, role })
```

**若不扩签名，名称 / 目标 / 摘要 / 文档会静默丢失**，落库的版本行只有 `changeNote`，表现为"提交成功但列表多列全是 `—`"。这是最容易被误判为"渲染 bug"的实现陷阱，需在联调前明确。

提交成功后的反馈：`message.success('BP 已更新为 V1.2')` → 关闭浮层 → 列表刷新、新版本置顶。

| **Q5** | AI 摘要的生成依据是否可读文档正文 | A：正式版接文档解析；B：仅依据已填字段归纳 | **A**（正式版）。B 的摘要信息增量有限，字段易被判定"无用"（§7.2） | 依据不定 → 摘要质量预期与验收标准无法对齐 |
| **Q6** | 是否提供"重新生成 AI 摘要"与历史版本删除/回滚 | A：提供重新生成，不提供删除；B：两者都提供；C：都不提供 | **A**。重新生成成本低、体验好；删除/回滚违反"版本记录不可变"，且业务未提 | 若业务实际要删除，需重新设计留痕与审计口径 |
| **Q7** | OPS（③ 系统运维预算）是否同期页面化 | A：本轮不做，后续统一；B：同期一并页面化 | **A**。本轮范围收敛；但需接受"三种下钻两形态"的暂态（§2.4） | 一并做则本轮范围扩大约 40%，且与 v0.8 未落地形成交叉 |
| **Q8** | 是否扩展全局搜索前缀支持 `BP-` | A：本轮不做；B：做 | **A**。BP 记录 id（`BP-2027-RETAIL`）当前不在搜索前缀白名单，扩展属独立需求 | 不做则用户无法从顶栏直达某部门 BP（可接受，主表入口已够） |
| **Q9** | 提交权限：是否仅业务部门可提交（Digital 只读） | A：沿用 v0.5（仅业务）；B：Digital 也可代填 | **A**。v0.5 已定稿；B 会破坏"业务对 BP 内容负责"的权责口径 | 权责不清，后续无法判断版本异常由谁负责 |

**本轮已可推进的前提**：Q1 采用推荐解释 A。**Q1 / Q2 是硬阻断项**——二者未拍板前，§4 列规范与 §5 数据模型不宜开工。

## 十一、名词表

统一术语，避免同一实体两个叫法。

| 术语 | 定义 | 与现状/用户表述的关系 |
|---|---|---|
| **年度 BP** | 编制项 ①，业务部门年度的业务规划文档/链接 | 既有术语（`BudgetModule.jsx` 83 行 `STAGE_LABEL`）；用户称"年度BP" |
| **年度 BP 计划**（页面） | 部门下钻页，主体 = 该部门全部 BP 版本列表 | 用户命名；对应现有 `BpPanel`（浮层）的页面化 |
| **BP 版本** | 一次提交产生的一条记录，含名称 / 量化目标 / 摘要 / 文档 / 修订说明 | 用户称"一个版本的年度BP计划" |
| **当前版本** | 版本列表中最新的一条（`bpVersions[0]`），即主表列显示的版本号 | 新增术语；取代 `BP_RECORDS.version` 的独立地位 |
| **不可变版本** | 已提交版本的内容不得再编辑；更新 = 追加新版本 | 本需求的隐含规则（§1 第 2.3 项） |
| **AI 摘要** | 业务留空「BP 内容核心摘要」时由 AI 生成并落库的文本快照 | 本需求新增（§7） |
| **AI 生成中** | 摘要异步生成中的中间态（`summarySource='ai_pending'`） | 本需求新增 |
| **文档链接** | 该版本 BP 的文档载体，`kind ∈ {link, file}`，可多条 | 用户用词；现状以 `docKind / docRef / docCount` 表达 |
| **修订说明** | 该版本相对上一版的变更说明（`changeNote`） | 用户用词；现有字段名 `changeNote` |
| **下钻页** | 从主表编制项进入的独立页面（本页与 v0.8 的《项目预算计划》） | 新增术语；与浮层相对 |
| **编制年** | 年度预算计划的编制口径年度，固定 `PLAN_FY = 2027` | 既有术语（`BudgetModule.jsx` 70 行） |
