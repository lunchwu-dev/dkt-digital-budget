## 3. 单元格信息层级重构（本次核心）

### 3.1 旧版式的问题

v0.5.1 是「`[状态 Tag] 主数值` ＋ 次数值一行」。`antd Tag` 自带底色和边框，
视觉重量跟主数值同级甚至更高 —— 结果「已确认」这个**过程信息**被顶到第一眼，
而真正要看的钱和条数是第二眼才看到。**主次颠倒了。**

### 3.2 新版式

```
┌────────────────────────┐
│ 304.8 万元             │  ← 主数值 16px / 500 / tabular-nums，单位以 12px 小字后缀
│ ● 已确认 · 4 条需求     │  ← 状态圆点（antd Badge，语义色）+ `状态 · 次数值`，12px / t3
└────────────────────────┘
```

| 编制项 | 第 1 级（产物） | 第 2 级（状态） |
|---|---|---|
| ① 年度 BP | `V2.1`；未提交 → `—`（淡色） | `● 已提交` |
| ② 项目预算 | `304.8` + `万元`；待评估 → `待核定`（淡色）；未提交 → `—`（淡色） | `● 已确认 · 4 条需求` |
| ③ 系统运维预算 | `830.8` + `万元`；未出具 → `待出具`（淡色） | `● 已确认 · 3 个系统` |

三个关键手法：

1. **状态从 Tag 降级为 Badge 圆点。** 圆点是纯色小点，能扫、能辨色（success / processing /
   warning / default 四档语义色），但没有底色和边框，不跟主数值抢焦点。
   `Badge` 的 `status` 取值与既有 `STATUS_TONE` 映射完全兼容，映射表一行没改。
2. **无产物时主数值降为淡色**（`c.t1` → `c.t3`）。扫表时空白一眼可辨 ——
   这比给「待核定」加个警告色更有用，因为它表达的是"这里还没有东西"，不是"这里出问题了"。
3. **单位「万元」以小字后缀**，不跟数字同号。数字位保持 `tabular-nums`，三列数值纵向对齐。

### 3.4 一个必须说明的口径修正（自我发现）

重构合计行时发现原口径**自相矛盾**：

- 主表列内：只有「当前版本已确认」才显示金额，整体变更后最新版本回到「待评估费用」、
  列内显示「待核定」；
- 但按「找该 BU 最新一个已确认版本」去求和，会把 **D-CRM 被变更覆盖掉的旧版本 V1.0（267.9 万元）**
  算进合计 —— 列内显示「待核定」，合计里却有钱。求和 713.0 万元 ≠ 列内可见金额之和。

**修正**：在 `annualPlanRow` 新增 `demandConfirmedAmount` —— 该 BU **当前版本已确认**时的费用（元），
未确认时为 `null`。它与列内显示的那个数**是同一个来源**，合计只累加它，不做任何回退估算。

- 修正前合计：713.0 万元（含被覆盖的旧版本，且与列内不一致）
- 修正后合计：**445.1 万元** = 零售运营 304.8 + 客户服务 140.3，覆盖 **2/8** 个 BU

被覆盖的旧版本金额仍留在版本记录表里可回溯，只是不再计入当前合计。
下方口径脚注也补了一句，说明它与上方 KPI 卡「总项目费用（清单当前版本）」（含业务预估的口径）
是**两个口径**，避免 445.1 与 2,790.5 并列时被误读。
