# v1.6 三大能力评审：年度预算计划 / 预算消耗 / 对账单

评审范围：`src/pages/BudgetModule.jsx`（annual + consume 双分支）、`ProjectBudgetPage.jsx`、
`OpsBudgetPage.jsx`、`BillingModule.jsx`、`DeptBillPage.jsx`、`BillFloors.jsx`、
`TrendChart.jsx`、`src/domain/calc.js`、`src/store.jsx`、`src/data/mock.js`。
所有数据结论均实跑 `calc.js` + `INITIAL_DATA` 复算，非推理。

## 0 结论前置

**三大块 10 个 P0 缺陷里，8 个是同一个根因：同一个业务事实存在多条取数路径，口径没有单一出处。**

这不是"若干处没写对"，是结构性问题：

- 运维预算：`opsAnnualEstimate`（年化）与 `opsIssued`（是否出具）两个门槛并存 → 主表列内显示「待出具」但合计照加，差 442.2 万
- 项目预算：年度页用清单费用合计（`demandAmount`），消耗页用「总包 − 运维」残差 → 同 BU 两个数，差 −188.3 ~ +103.1 万
- 累计口径：消耗页用 `isConfirmed`（仅 CONFIRMED），账单页用 `billStateOf !== 'DRAFT'`（含 SENT）→ 差 369.4 万
- 部门账单：详情页 3 卡用全量月份，两个明细楼层用 `billedMonthsOf` → 差 571.2 万（8/8 部门全中）

**这四处都是「同一屏里两个数对不上」，且都是默认态必然触发。** 演示时只要用户按列加一遍、或在两页间跳一次，数据可信度就崩了。这类缺陷的修复收益远高于任何交互/视觉优化。

已定稿的纪律（"合计与明细同源"）其实**只在单个文件的单个组件内被执行了**，从未跨到文件边界。修复方向不是逐处打补丁，而是把口径判定上提到 `calc.js` 并让两侧引用同一函数。

另外两条独立于口径的主线：
- **流程可达性**：项目预算页对 2/8 部门的「编辑」按钮 100% 失败，且失败原因不在界面上
- **可发现性**：交付明细 9 列 1312px，1366 屏首屏恰好丢掉价值/费用/ROI 三列 —— 账单页看不到金额

## 1 P0 · 数据可信度（必修，演示前）

### P0-1【最高杠杆】项目预算两页不同源 → 消耗页极端值是残差法的产物

| | |
|---|---|
| 位置 | `src/domain/calc.js:525`（`projectBudget = pool.total - opsBudget`）vs `calc.js:852`（`projectAmount = demandAmount`） |
| 实测 | FY2026：D-RETAIL 消耗页 436.3 万 / 年度页 248.0 万（差 −188.3 万）；D-SVC 30.9 / 134.0（+103.1 万）；D-MKT 44.3 / 116.9（+72.6 万）。**8 个部门 8 个不一致** |

消耗页的「项目预算」是残差（总包减运维），年度页是清单费用合计（真相源）。残差不承担业务含义 —— 它只是让「整体 = 项目 + 运维」这条恒等式成立。

**连带**：D-SVC 总包 140 万、运维 109.1 万，项目只剩 30.9 万 → 消耗率 **294.8%**；D-MKT 项目侧 106.5%、FY2027 D-MKT 170.7%。**这些 >100% 不是 mock 造的假象，是残差法压小分母的必然结果。** 档位阈值 0.7/0.9/1.0 是按总包量级设计的，套到残差分母上语义失效。

修法：`projectBudget` 改直取 `demandAmount`；差额作为独立字段 `projectGap` 显式暴露。**改完极端值应自然收敛** —— 若仍 >100% 则属真实超预算，保留并在 `segTip` 补「已透支 X 万（弹性透支策略，不阻断提报）」。

### P0-2 部门账单详情页 3 卡把待出账月算进「累计」

- 位置：`src/pages/DeptBillPage.jsx:49-63`（`deptMonthRows` 用 `data.months.map` 全量）、`:82-90`（`agg` 直接 Σ）
- 对照：`calc.js:1362` / `calc.js:1441`（两个明细楼层用 `billedMonthsOf`）
- 实测：差异精确等于该部门 2026-09（DRAFT）的 `buildBill().total`，**8/8 部门全部匹配**。D-RETAIL 差 119.4 万（相对偏差 16.8%）
- 根因：`deptMonthRows` 复制了 `store.derived.monthRows` 的写法，而那是**趋势图**取数 —— 趋势图本就该含 DRAFT。趋势序列被直接当成"累计合计"复用
- 附带：`agg.deliveryCount` 取 `billedMonthsOf` 口径（8 个月，对），`agg.delivery` 取 12 个月口径（错）→ **同一张卡片的 label 与 sub 用了两个口径**
- 修法：`rows` 保持全月份（趋势图需要），`agg` 改从 `billedMonthsOf` 取边界；更彻底的做法是直接复用 `deliveryBillRows(data, month, deptCode).totalAmount`（符合该文件 `:25-26` 自述的"不做任何累加"纪律）

### P0-3 主表运维列「待出具」的行，金额照样进合计

- 位置：列内条件 `BudgetModule.jsx:429`（`r.opsIssued ? ... : '待出具'`）vs 合计 `BudgetModule.jsx:326`（`rows.reduce((s, r) => s + r.opsAmount, 0)` 无条件累加）
- 门槛：`calc.js:882` `opsIssued = !!(opsPlan && opsPlan.issueDate)`
- 实测：D-MKT（编制中）+ D-HR（未启动）显示「待出具」，用户逐列相加得 25,473,671 万，合计行显示 29,895,502 万，**差 4,421,831 万无解释**。④列与总预算列同受影响
- 加重：页头指标卡把这个数标为「系统运维预算（Digital 出具）」（`:521`），而其中 442 万根本没出具
- 修法：加 `opsCountedAmount`（`opsIssued || 待确认草稿` 时取值，否则 0），合计与 ④列统一改用；或反过来对"有派生值但未出具"的行显示派生金额 + `muted` + title 说明。**二者选一，但必须让 `sum.opsAmount ≡ Σ列内可见值`**。同时删掉指标卡 label 里的「Digital 出具」这一不实描述

### P0-4 消耗页合计行与筛选结果脱钩

- 位置：`BudgetModule.jsx:1710-1729`（summary 用 `overview`）vs `overview` 来自 `allRows`（`:1431`/`:1444`），而表格数据源是筛选后的 `rows`（`:1464`）
- 实测：筛选「部门 = 零售运营」后表格 1 行、FilterBar 显示「共 1 条」，**合计行仍显示全公司 4440.0 万 / 56.6%**；楼层二标题「透支 1 个 · 预警 0 个」（`:1685`）与 Hint 告警同样基于未筛选的 `allRows`
- 根因：`overview` 语义是"全量汇总卡"，被复用为"当前可见行的合计"，两种语义混用
- 修法：拆成 `overview`（`allRows`，供三张卡）与 `tableSummary`（`rows`，供合计行）；透支/预警计数与 Hint 同步改用 `rows`

### P0-5 消耗页与账单页「累计」口径差 369.4 万

- 位置：`calc.js:545`（`isConfirmed`，仅 CONFIRMED）vs `calc.js:1336-1337`（`billStateOf !== 'DRAFT'`，含 SENT）
- 实测：消耗页「已核销」1964.9 万 → 查账进部门页累计态「合计应收」2334.3 万，**差 369.4 万**（SENT 的 2026-08）
- 影响：查账的唯一用途就是核对，对不上则整个消耗页失去参考价值
- 修法：拆成两个具名口径 —— `billedMonthsOf(data, 'CONFIRMED')`（消耗页用）与 `billedMonthsOf(data, 'NOT_DRAFT')`（账单页用），名字自带语义；账单页累计态标题改「累计应收（含已发出待确认）」

### P0-6 D-CRM 已确认 V1.0，下钻页却显示「已核定 0 条」且总额差 114 万

- 位置：`mock.js:348` 起三条需求 `evalAmount` 全为 `null`，而 `DV-CRM-1` 是 `status:'已确认'` `totalAmount: 2,679,000`
- 现象：概览卡「当前版本 V1.0 / 确认于 2026-09-22」，紧邻「项目总费用 279.3 万 · 3 条 · 已核定 0 条」。版本号已确认、状态待评估、已核定 0 条、金额既不等于版本记录也不等于主表
- 根因：`calc.js:993` `demandAmount` 对 `evalAmount == null` 回退 `estAmount` → 2,793,000，与版本记录无任何约束
- 加重：D-CRM 是唯一"已有已确认版本 + 又有进行中版本"的部门，最可能被当演示样例；ROI 因分母全 null 而 3 条全「—」
- 修法：补齐 mock 三个 `evalAmount`（使 Σ = 2,679,000，与 `DV-CRM-1.totalAmount` 严格相等），ROI 同时有值。若要保留该状态组合，概览卡在有进行中版本时并列显示「正式版 V1.0 = 267.9 万 / 本次编辑暂计 X 万」

### P0-7 需求清单提交后无撤回路径

- 位置：`ProjectBudgetPage.jsx:816-829`（`EDIT_PERMISSION` 无 S3 业务字段）、`store.jsx:466-505`
- 现象：业务 S2 提交 → S3「待 Digital 反馈费用」后清单全部只读，且无「撤回」按钮。发现一条写错，唯一出路是「废弃新版本」—— 该动作连带删除已提交的 `demandVersion`（`store.jsx:499-505`），等于整份清单重录
- 根因：状态机缺 S3→S2 回退边。设计文档把 S3 定义为"清单不可再改"，但没给业务留纠错通道
- 附加风险：S4 状态下「废弃新版本」同样存在且无二次确认，业务可把一条已提交待确认的版本直接销毁
- 修法：加「撤回修改」（S3→S2，删对应 `demandVersion`、退回进行中版本号），二次确认文案「撤回后清单回到可编辑状态，Digital 已反馈的费用将一并丢弃」；S4 废弃加二次确认 + 说明"已提交内容将不可恢复"

### P0-8【流程死路】2/8 部门的「编辑」按钮 100% 失败，且原因不在界面上

- 位置：`ProjectBudgetPage.jsx:669-672`（`onEdit` 直接改 hash）vs `:133-146`（`isNew && !pg.hasInProgress` 时 `setTimeout(0)` 无条件 `window.location.replace` 回基础路由）
- 根因：`enterEdit`（`:187-190`）有 `startDraft` 前置，`onEdit`（`:669`）没有 —— **两条进入 `/new` 的路径前置条件不一致**
- 实测：`DRAFT_SEEDS`（`mock.js:590-605`）只含 D-CRM/D-ECOM/D-SCM/D-MKT/D-FIN/D-HR，**D-RETAIL（4 条已确认需求）与 D-SVC 无草稿** → 这 2 个 BU 的详情编辑必然失败
- 现象：点「编辑」→ 地址栏变 `.../new/DM-2027-0001` → 立刻弹回 `.../project/D-RETAIL`，全程只闪一句「当前无进行中版本」，**界面无任何"要先点右上角编辑"的提示**
- 加重：这两个部门恰好是数据最完整、最像"标杆"的部门
- 修法：`onEdit` 内先 `if (!pg.hasInProgress) startDraft(deptCode, PLAN_FY)` 再跳（`BudgetModule.jsx:624-629` 的 SummaryPanel ②卡已是这个写法）；或删掉 `window.location.replace` 兜底，在 `DemandEditPage` 内补 `startDraft`，让深链 `/new/{demandId}` 本身成为合法建草入口
- **改动量约 5 行，收益最高的一条**

### P0-9 查账跳转丢 FY 上下文，且无法跳回消耗页

- 位置：`BudgetModule.jsx:1605`（`onNavigate('billing','dept', r.deptCode)`）→ `DeptBillPage.jsx:67`（**只解构 `data`，未取 `globalFy`**）→ 返回按钮 `:138` 写死 `onNavigate('billing','monthly', deptCode)`
- 现象①：在 FY2027「编制中」视图点查账，落到账单页看到 FY2026 已核销账单，**页面无任何 FY 标识**，用户无法察觉年度已切换
- 现象②：返回按钮回的是「对账单总览」而非来路「预算消耗」，要退回必须连点两次返回
- 现象③：路由 `tail` 段已被项目预算页占用，`dept` 视图无位置放 FY
- 修法：`#/billing/dept/{deptCode}/{fy}`（复用 `tail` 段，`App.jsx:111` 已解析、`go()` 已透传）；DeptBillPage 在 `BillingHeadBar` 副标题标明年度；返回按钮按来路判断，无来路才回 `billing/monthly`，文案随之改为「返回预算消耗」

### P0-10 BP 版本一旦提交，无任何修正或废弃入口

- 位置：`BudgetModule.jsx:851-858`（唯一入口「修正年度 BP」）、`store.jsx:160-198`（只追加，无删除/置废）
- 现象：BP 文档链接填错、年度目标写错、修订说明贴错 → 只能再提交一个新版本，**错误内容永久留在版本列表**。三个下钻页里只有 BP 列表页没有版本操作列（项目预算页有废弃/退回，运维页有退回）
- 修法：BP 列表加窄操作列（≤76px），当前版本（index 0）提供「废弃」+ 二次确认「废弃后该版本不再作为当前版本，BP 回到 V{n-1}」；store 过滤该 version 记录 + 留痕，版本号由剩余历史重算 —— 与 `discardDraft` 纪律一致

### 可发现性 / 可读性

**P1-11 交付明细 9 列在 1366 屏恰好把最右 3 列推出首屏** — `BillFloors.jsx:36-47`

按项目自己的核算式（`BillingModule.jsx:292`：1366 可用宽 ≈ 1047px）逐列累加：
`brdId 132 → title 322 → desc 582 → dept 692 → goLive 802 → retro 952 → value 1082 ✕ → fee 1222 ✕ → roi 1312 ✕`

**首屏恰好在「业务复盘文档」列结束，最该被看到的「业务量化价值 / digital 费用 / ROI」三列全在折叠区右侧。** 用户读一张账单，第一眼看不到金额。运维 6 列同理：`shares`（分摊 BU 清单）在 1130 之外 —— 而"摊给了谁"正是运维楼层的核心信息。

成因：260px 给了"项目描述"（Tooltip 悬浮才看全，`maxHeight:40` 截断），三个数字列压到 130/140/90。
修法：`desc` 降为 180 + ellipsis，或移出主表；腾出的 80-100px 足够让 `value` 进首屏；`fee`（digital 费用）加 `fixed:'right'` —— 它是唯一必须常驻可见的列。

**P1-12 三块明细表全无排序、无搜索、无导出** — `BillFloors.jsx:193-200`、`BudgetModule.jsx:1575-1612`

交付明细累计态 17 行 × 9 列，横滚 265px 才看完，表格不分页。想找"ROI 最高的项目"只能逐行横滚。消耗页 8 行想按金额排也做不到（唯一排序是写死的档位优先+消耗率降序）。**v1.4.1 移除页面级筛选项后没补表内检索 —— "移除筛选"被误当成了"不需要查找"**。

## 3 P2 · 视觉与一致性

**P2-1 四个楼层顶部色条同色，层级无法区分** — 6 处 `borderTop: 3px solid` 里 5 处是 `c.brand`（`BillFloors.jsx:308` 运维用了 `c.meterCommitted`）。趋势图/费用构成/交付明细/部门账单在视觉上是"同一类东西"，读者无法从色条判断"这屏是汇总还是明细"。建议汇总类用 `c.brand`、明细类用 `c.border` 或 `c.t4` 中性色条。

**P2-2 「分摊 BU 清单」列行高失控** — `BillFloors.jsx:289-300`，`width: 320`。实测 SYS-07（数据仓库与 BI）分摊 8 个 BU，单行高约 184px，而 SYS-05/06/08 只有 1 个 BU（58px）。8 行表格高度被一个单元格撑到 3 倍，视觉重心失衡。超过 3 个折叠为"数据仓库与 BI 等 8 个 BU" + Tooltip 列全量。
