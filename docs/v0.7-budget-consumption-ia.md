## 2. 先做一个判断：4 张卡 → 3 张卡

原文写「四个卡片变为如下内容」，但列出的内容只有 3 项。这**不是文案疏漏，而是必然**：

旧四卡 = 预算总包 / 项目费用预算 / 系统运维费用预算 / 截止当月消耗进度。
新第 1 项「整体预算总包**，整体消耗进度**」把旧第 1 张与旧第 4 张合并成了一件事 ——
「截至当月消耗进度」本来就是「整体总包的消耗进度」，过去拆成两张卡是重复。

所以本次交付的是 **3 张卡**。如果你要的是 4 张（比如把「可用余额」或「已承诺」独立成卡），
说一声，加一张是一行代码的事 —— 但会重新引入重复。

## 3. 楼层一：整体预算消耗情况（3 张卡）

三张卡同构，自上而下六级信息：

```
① 各部门数字化整体预算总包                      [正常 · 56.6%]
4,440.0 万元
▓▓▓▓▓▓▓▓▓▓▓░░░░░░░░░░░░░░░░
截至当月已消耗                          2,511.2 万元 · 56.6%
已核销 1,964.9 · 已承诺 546.3 · 可用 1,928.8 万元
覆盖 8 个业务部门 · 整体预算 = 项目预算 + 运维预算
```

| 卡 | 总包 | 消耗 | 消耗率 | 构成明细 |
|---|---:|---:|---:|---|
| ① 各部门数字化整体预算总包 | 4,440.0 | 2,511.2 | 56.6% | 已核销 1,964.9 · 已承诺 546.3 · 可用 1,928.8 |
| ② 项目预算总包 | 1,665.2 | 966.7 | 58.1% | 已核销 420.4 · 已承诺 546.3 · 可用 698.5 |
| ③ 运维预算总包 | 2,774.8 | 1,544.5 | 55.7% | 已核销 1,544.5 · 无「承诺」中间态 · 可用 1,230.3 |

**进度条直接复用既有的三重口径进度条 `PoolMeter`**，没有新造轮子：

- 执行年度（FY2026）：呈现「已核销 / 已承诺 / 可用」三段 + 100% 总包刻度线；
- 编制年度（FY2027）：没有实际核销，唯一可看的进度就是「已规划」的位置，
  故改用 `PoolMeter` 的**已规划虚线标记**，看起来就是「计划打在这里」。

三张卡的右上角各挂一枚档位标签（正常 / 关注 / 预警 / 已透支），**按各自维度的消耗率独立判定** ——
所以能出现「整体正常 56.6%，但项目侧 58.1%、运维侧 55.7%」这种结构性差异被显性化的情况。

## 4. 楼层二：部门预算消耗情况

### 4.1 表格结构：三组「预算及消耗」列

表头改为**两层**（antd 分组表头），父表头就是用户指定的三个口径：

```
业务部门 │ 整体预算及消耗 │ 项目预算及消耗 │ 运维预算及消耗 │ 状态 │ 操作
         │ 预算 | 消耗    │ 预算 | 消耗    │ 预算 | 消耗    │      │
```

- **预算子列**：金额（14px 常规色）+ 脚注「总包 / 占 X%」；
- **消耗子列**：消耗金额（14px / 500）+ 细进度条 + 「已消耗 56.6%」。
  进度条**按该维度自身的档位取色**（透支红 / 预警橙 / 关注蓝 / 正常绿），
  于是「整体正常、但项目侧已被击穿」这类问题在行内一眼可见，不必点进抽屉。


## 5. 「调整预算计划」→「调整项目预算」业务分支

### 5.1 旧口径的问题

v0.6 及以前，行内「调节额度」直接弹一个 Modal，两步：填金额 → 提交。
它**没有任何业务约束** —— 可以把额度压到低于已核销金额，页面照样接受，这笔账之后就对不上了；
作业面也不清楚「这笔调整到底动的是整包还是某一侧」。

### 5.2 新分支（Drawer）

```
业务分支：调整项目预算
  说明：调整对象为项目预算；运维预算由计费模型年化锁定，不随人工调整变化；
       因 整体预算 = 项目预算 + 运维预算，本次调整将使整体预算同步增减同等金额。

当前预算构成（FY2026）
  口径     预算(万元)  已消耗(万元)  进度
  整体      140.0       154.4      110.3%      = 项目 + 运维
  项目       30.9        91.2      294.8%      本次调整对象
  运维      109.1        63.2       58.0%      计费模型锁定，不可调

调整内容     [追加额度 | 压降额度]   [ 80.0 万元 ]   调整对象：项目预算
            调整依据（必填）

影响预览     调整后项目预算 110.9 万元 (+80.0) │ 调整后整体预算 220.0 万元 (+80.0) │ 调整后项目消耗率 82.2%（原 294.8%）
             ✅ 校验通过：调整后项目预算 110.9 万元 ≥ 已消耗 91.2 万元

调整流水     时间 / 调整对象 / 金额 / 操作人 / 调整依据
```

**硬校验（界面上先行拦截，提交时 store 兜底）**：

| 情况 | 结果 |
|---|---|
| 调整后项目预算 < 已消耗（已核销 + 已承诺） | 红色拦截，禁用提交。文案点明「已承诺（BRD 签收锁价）不可回撤，压降后仍会照常出账」，并给出本轮最大可压降额度 |
| 调整后项目预算 ≤ 0 | 红色拦截，禁用提交 |
| 未填金额 / 未填依据 | 禁用提交 |
| 通过 | 绿色放行，并给出消耗率变化（由 X% 变为 Y%） |

**为什么把「已消耗」设为下限**：已核销是真金白银、已承诺是签收锁价（合同义务），
两者都不可能因为「预算被压降」而消失 —— 允许压到下限以下，等于制造一笔注定对不上的账。
「追加不设硬性上限」是有意为之：追加只会让整体预算抬升，风险由年末调节窗口统一接管，
这条策略与页面顶部既有的「弹性透支 + 年末调节」一脉相承。

**写入**：`store.adjustProjectBudget()` —— 同步改 `poolFY26/27`、写 `poolAdjustments` 流水
（新增 `target: 'PROJECT'` / `branch: '调整项目预算'` 两个字段，便于将来按分支筛选）、
写审计日志。实测：D-SVC 追加 80 万元 → 项目预算 30.9 → 110.9、整体预算 140.0 → 220.0、
档位由「已透支 110.3%」变为「关注 70.2%」。

## 6. 口径（三段式，恒等式可回归校验）

| | 项目侧 | 运维侧 | 整体 |
|---|---|---|---|
| 预算 | 总包 − 运维年化预算 | 计费模型 12 个月年化（× 编制年增长系数） | 部门预算总包 |
| 执行年消耗 | 项目已核销 + **已承诺** | 运维已核销 | 项目消耗 + 运维消耗 |
| 编制年「消耗」 | 已规划（需求清单预估） | 恒为 0 | 已规划 |

两个要点：

1. **「已承诺」全部计入项目侧**。承诺（签收锁价、尚未出账）只可能来自 BRD 交付，运维是按月计费的，
   没有「承诺」这一中间态 —— 所以运维卡上明写「无「承诺」中间态」。
2. **三个维度的分母不同**（各自的总包），消耗率**不可相加**；可相加的只有金额：
   `整体 ≡ 项目 + 运维`，这一条已写成断言（读三张卡的金额，断前后差 < 0.05 万元）。

口径实现收口在 `calc.consumptionBreakdown()` 一处：卡片与表格**都从这里取数**，
视图里不做任何累加（视图内自行累加是历史上「卡片和合计对不上」的根源）。

## 7. 一个需要你拍板的口径问题（自我发现）

把项目侧单独拎出来看之后，暴露了一个此前被整体消耗率掩盖的现象：

```
客户服务    项目预算  30.9 万元   项目已消耗  91.2 万元   → 294.8%
市场营销    项目预算  44.3 万元   项目已消耗  47.2 万元   → 106.5%
```

根因是**项目预算一直是个余量**：`项目预算 = 部门总包 − 运维年化预算`，运维侧按计费模型刚性占用，
余下的才留给项目。客户服务总包 140 万，运维刚性吃掉 109.1 万，项目只剩 30.9 万，
而实际项目消耗 91.2 万 —— 数学上必然溢出。

这**不是 bug，是现有口径的必然结果**，而且我认为它值得被显性化（页面已经用红色进度条把它标出来了）。
但请你决定后续方向：

- **A. 保持余量口径**（现状）：项目侧超标是「运维挤占项目」的真实信号，但「项目预算」这个数
  不能被当作「项目侧的花钱上限」来解读；
- **B. 改为独立编制口径**：项目预算由需求清单核定费用独立给出（业务已提交、Digital 已确认的那个数），
  运维预算独立编制，两者之和**不必等于**总包，差额单独作为「未分配余量」列示。
  口径更正，但会牵动《年度预算计划》的 `budgetComposition` 与账单模块的对账逻辑。

**我没有替你做这个决定** —— 它改的是钱的算法，不是版式。
