## 0. 一句话定位

**管同一个「钱」在三个时间点的三种形态：预算期是额度、交付期是承诺、计费期是核销；每一张账单行都必须能回答「它来自哪个需求、哪个部门 BP」。**

## 1. 业务问题与产品目标

### 1.1 现状痛点

| 痛点 | 表现 | 产品对策 |
|---|---|---|
| 预算编制无版本留痕 | BP 用 Excel 反复覆盖，年底无法回溯「当时为什么这么报」 | BP 台账 + 版本链（仅追加，不可静默改写）+ 废弃通道 |
| 需求与预算两张皮 | 需求清单与预算池各自维护，合计对不上 | 预算池三口径记账，`整体 = 项目 + 运维` 恒等式可断言 |
| 计费口径不可解释 | 账单金额只看得到总数，问不出「为什么是这个数」 | 每张账单行强制携带 `demandType / changeType / pricingBasis` 三个标注 |
| 超支发现太晚 | 通常到年底财务决算才知道超了 | 消耗页四档预警（正常 / 关注 / 预警 / 已透支），按月累计 |
| 变更吃掉预算 | CR 变更混在交付里，量看不出来 | CR 独立节点、独立计价、独立追溯 |

### 1.2 产品目标（可验收）

1. **可追溯**：任一账单行 → BRD → 年度需求 → 部门 BP → 预算池，五跳内闭环。
2. **口径一致**：同一业务事实全站只有一个取数函数（`src/domain/calc.js`），视图内禁止自行累加。
3. **过程留痕**：编制项的每一次提交 / 更新 / 出具 / 复核确认都落一条活动记录，不可逆动作（废弃、确认）必须留痕。
4. **离线可演示**：`dist/index.html` 双击即开，无后端依赖，可直接进评审会。

### 1.3 非目标（本版本明确不做）

- 不做真实后端与持久化（当前为内存 mock + `localStorage` 级演示态）。
- 不做真实单点登录与组织架构同步。
- 不做计费规则的可视化配置（计费规则页仍在「未完成」区）。
- 不做多租户。

## 2. 角色与场景

### 2.1 角色矩阵

| 角色 | 典型动作 | 主战场页面 |
|---|---|---|
| **业务部门 · 预算专员** | 编制次年 BP、提交需求清单草稿、复核 Digital 反馈的费用 | 年度预算计划 / 年度 BP 计划 / 项目预算计划 / 系统运维预算计划 |
| **Digital · 整合与评估** | 出具运维规划、评估需求费用、签收 BRD、驳回重提 | 项目预算计划 / 需求受理 / 评估与签收 |
| **财务 / 结算** | 逐月出账、发出账单、确认核销 | 对账单总览 / 部门账单详情 |
| **部门负责人** | 只读查看本部门三口径进度与超支风险 | 预算消耗 |
| **平台管理员** | 基础数据（部门、系统、费率卡）维护 | 设置抽屉 |

### 2.2 关键场景

**S1 · 编制次年预算（当年 Q4）**
业务部门提交 BP（生成 v1.0）→ 在《项目预算计划》拉起需求清单草稿 → 逐条录需求 → 提交 → Digital 反馈费用 → 业务复核确认 → 需求得号（`DM-2027-xxx`）→ 《系统运维预算计划》录运维预估 → 提交 → Digital 出具 → 业务确认 → 进入整合评审。

**S2 · 需求交付与计费（次年滚动）**
BRD 提报（强制关联年初需求，否则必须填「年度新增原因」）→ Digital 评估（人天 × 费率卡）→ 签收锁定评估价 → 交付上线 → 按月出账单 → 发出 → 确认核销。

**S3 · 月度对账**
《对账单总览》选账期 → 看交付 / 运维两栋明细 → 下钻部门账单详情 → 核销确认或退回。累计态可看全年走势。

**S4 · 超支预警**
《预算消耗》按部门看三口径进度条与档位；点进部门可拆「已规划 / 已承诺 / 已核销 / 透支」四段。

### 3.2 信息架构原则（v1.5 定型）

- **已上线的页平铺在顶部，直接可点**，不套文件夹。
- **未完成的页全部收进底部唯一的「未完成」文件夹**，组标题带「规划中」标记 —— 解决 v1.4 时期「已上线页与半成品视觉同级、点进去才发现是半成品」的问题。
- **站点说明书单列一档**：它不是第四块业务能力，放进「未完成」是错误标签，并排会误导。
- 路由段 `module/view` **保持不变**，只改呈现层 —— 深链、书签、全局单号搜索（`DM-` / `BRD-` / `CR-` / `BILL-`）零影响。

## 4. 核心业务规则

### 4.1 三口径记账（不可妥协）

| 口径 | 含义 | 计入内容 |
|---|---|---|
| **已规划** Planned | 预算期承诺要花的钱 | 已确认的 BP + 需求清单 + 运维预估 |
| **已承诺** Committed | 交付期锁定要花的钱 | 已签收 BRD 的评估价 + CR 增量 |
| **已核销** Billed | 计费期实际已花的钱 | 已确认账单的账单行 |

恒等式：`已核销 ≤ 已承诺 ≤ 已规划`，且 `整体 = 项目侧 + 运维侧`。这两条以断言形式写在冒烟测试里，口径漂移会立刻 FAIL。

### 4.2 档位阈值

| 档位 | 消耗率 | 语义 |
|---|---|---|
| 正常 `ok` | < 70% | 健康 |
| 关注 `watch` | 70% ~ 90% | 进入视野 |
| 预警 `warn` | 90% ~ 100% | 逼近上限 |
| 已透支 `over` | ≥ 100% | 击穿 |

> **口径说明（不是 bug）**：执行年（FY2026）四档齐全；编制年（FY2027）因运维预估全额计入分母，整体侧最多到「关注」。这是模型的硬约束 —— 要落「预警」就得让池额小于运维预��，页面显示「透支」，那是「不够花」而非「花得快」，属另一种语义，不制造。

### 4.3 费率规则

- 费率卡**预算期锁定，全年不调价**。
- 交付计费：`人天 × 费率卡`，按 BRD 评估行计。
- 运维计费三型：
  - `order` 订单量 × 单价
  - `member` 规模（千人）× 单价
  - `fixed` 年费 / 12 × 部门份额
- 运维计量用**确定性伪随机 + 季节性系数**（种子 = FNV-1a(系统|部门)），保证同一月份任意次打开数值一致 —— 否则截图对不上，评审会直接失去信任。

### 4.4 变更（CR）独立计价

CR 不并入原 BRD 金额，独立成行、独立标注 `changeType`，是次年压增的依据。

### 4.5 弹性透支，而非硬熔断

系统不做提交拦截，只做档位预警 + 留痕。理由：预算编制期的「超」往往是业务判断的结果，系统硬拦只会让人绕过系统；把超支显性化并归因到人，比拦住更有管理价值。

## 5. 关键流程与状态机

### 5.1 需求清单状态机（项目侧）

```
（草稿不存在）
   │ startDraft
   ▼
草稿 ──submitDraft──▶ 待反馈费用 ──evaluateDraft──▶ 待复核确认
  ▲                        │                            │
  │ withdrawDraft          │ rejectDraft               │ confirmDraft
  └────────────────────────┴────────────────────────────┤
                                                        ▼
                                                  已确认（得号 DM-xxxx）
                                                        │
                                              discardDraft（废弃）
```

### 5.2 运维预算状态机

```
首稿明细 ──submitOpsDraft──▶ 待Digital出具 ──confirmOpsDraft──▶ 已确认
   ▲                              │
   │ saveOpsDraft                 │ rejectOpsDraft
   └──────────────────────────────┘
                    discardOpsDraft（任意阶段可废弃）
```

### 5.3 账单状态机

```
待出账 DRAFT ──sendMonths──▶ 已发出待确认 SENT ──confirmMonths──▶ 已确认核销 CONFIRMED
     ▲                                                              │
     └────────────────────── 退回（回到 DRAFT）──────────────────────┘
```

### 5.4 BRD 溯源六节点

`① BP 提交 → ② 年度需求 → ③ BRD 提报 → ④ 费用评估/签收 → ⑤ 交付 → ⑥ 账单核销`

节点状态的**唯一来源**是 `calc.traceOfBrd()` / `calc.traceOfDemand()`；`traceNodes.js` 只做字段到状态的翻译，不新增业务判断。

## 6. 数据模型（产品视角）

25 个实体，完整字段见根目录 `DESIGN.md` 第 4 章。产品侧需重点理解的 8 个：

| 实体 | 业务含义 | 关键约束 |
|---|---|---|
| `Department` | 业务部门 | 持有年度预算池 `poolFY26 / poolFY27` |
| `RateCard` | 费率卡 | 预算期锁定，全年不调价 |
| `BpRecord` / `BpVersions` | BP 及版本链 | 仅追加；可废弃但留痕 |
| `DemandItem` / `DemandVersions` | 年度需求及版本 | 得号后进入交付期 |
| `DemandDraft` | 需求清单编制草稿 | 正式 `demands` 的唯一写回点是 `confirmDraft` |
| `OpsPlan` / `OpsVersions` / `OpsDrafts` | 运维预算三件套 | 草稿 → 出具 → 确认 |
| `BRD` + `EvalLines` | 需求单与评估行 | 必关联年初需求；签收即锁价 |
| `Bill` + `BillLine` | 账单与账单行 | 一部门一账；行必带三标注 |

金额一律以**元**存储，展示层统一折算**万元**。

## 7. 非功能性要求

| 维度 | 要求 | 当前实现 |
|---|---|---|
| 离线可用 | 产物双击即开 | Vite 配置为相对路径 + 非 module 入口，`dist/index.html` 可直接打开 |
| 一致性 | 口径恒等式、排除项不得混入 | 冒烟测试以断言固化，反向证明法 |
| 可访问性 | 正文 13px 及以下对比度 ≥ WCAG AA 4.5:1 | 语义 token 分「填充色」与「达标小字色」两档，绿/橙压暗至 5.61:1 / 4.80:1 |
| 可维护性 | 同源事实单一出处 | 口径 / 路由 / 导航 / 色值各有唯一出处文件 |
| 留痕 | 不可逆动作可追溯 | `planActivities` + `auditLog` |

## 9. 已知限制与后续确认

1. **后端未接入**：所有数据在内存，刷新即回到初始态。P1 需落库并补幂等。
2. **交付域为规划态**：4 页在「未完成」区，交互深度弱于已上线页，评审时需说明。
3. **计费规则硬编码**：费率与计费型别写在数据里，P3 前不可配置。
4. **角色无鉴权**：所有操作可任意执行，权限矩阵目前只存在于设计文档。
5. **单年演示窗口**：FY2026 执行年 + FY2027 编制年并行，已足以演示「当年新增如何影响次年池」，但未覆盖跨三年滚动。
