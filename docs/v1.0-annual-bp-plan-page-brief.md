# v1.0 《年度 BP 计划》独立页面 · 需求基线（Requirement Brief）

> 文档类型：**需求发现产出 / 需求基线**。本轮**只产出本文档，不改任何源码**。
> 上一轮 v0.9 已对同一需求做过形式化；本轮在此基础上（a）复核作用域判定、（b）把用户原文已锁定的点从待确认清单中**移除**、（c）落地主理人点名的 Q1–Q7、（d）给出**可直接施工**的基线。
> 文中所有「现状」以当前代码为准，行号取自 `src/pages/BudgetModule.jsx`、`src/store.jsx`、`src/domain/calc.js`、`src/App.jsx`、`src/data/mock.js`、`tests/smoke.cjs`；与代码不符处以代码为准。
> **术语对齐**：用户本轮用词为「**修正年度 BP**」（v0.9 曾写作「更新年度 BP」）。本文一律以用户原文「**修正年度 BP**」作为按钮/浮层文案，内部动作语义仍为「提交 / 更新」。

## 一、结论前置（7 条最关键判断）

1. **页面作用域 = 「一个部门 × 一个编制年」`PLAN_FY = 2027`，判定成立（已复核）。** 依据见 §二·C1。用户第 1 点原文"点击**某业务部门的年度BP**"已把点击对象限定为**部门级产物**；第 2 点"每行一个版本"要求页面承载多行 ⇒ 对象必须可有多版本 ⇒ 只能是部门级。此点仍是**唯一会推翻整页结构**的分歧，列入待确认的"高影响确认项"，但**推荐答案坚定、不阻塞开工**。

2. **模型级阻断项（硬风险）：内容字段必须从 `BP_RECORDS` 下移到 `BP_VERSIONS`。** 现状 `BP_VERSIONS`（`mock.js` 165–175）仅 `id/fy/dept/version/at/owner/changeNote`，**无** 名称 / 量化目标 / 摘要 / 文档；`BP_RECORDS`（156–162）才存 `docKind/docRef/docCount`，但**只存当前版本一份**。不下移 ⇒ 用户第 2、3 点（每行一版本、每行 5 列）**无法渲染**。

3. **禁止双真相源。** 内容字段下移后，`BP_RECORDS` 不得再独立保存 `version/docRef/changeNote`（现状 `store.planAction` 99–128 行同时写两处）。**统一口径：版本列表（`BP_VERSIONS`）是唯一真相源，当前版本 = 列表首行**。否则主表列（读 `bpRecords`）与页面列表（读 `bpVersions`）迟早分叉。

4. **不新增任何状态（用户原文已自洽锁定 Q3）。** 用户第 4 点"提交后即更新对应业务BP" = **无草稿态、无复核态、无归档态**，与 v0.5 已定稿的"BP 只有 `已提交 / 未提交`"一致。**不得照搬 v0.8《项目预算计划》的 6 态状态机**——那会凭空给 BP 造出第二套生命周期。用户第 3 点"（自由文本格式）"亦已把 **Q2 量纲锁定为自由文本**，不再列为待确认。

5. **两条实现约束必须点名（硬风险）**：① 新路由 key **不能叫 `bp`**——已被 `LEGACY_VIEWS.budget.bp` 占用（`App.jsx` 62 行），且 `tests/smoke.cjs` 820–822 行断言 `#/budget/bp` 必须重定向到 `annual`；② `store.planAction` 当前签名只接 `note` 单字段（`store.jsx` 79 行），新浮层要落 5 个字段，**必须先扩签名为 `payload` 透传，否则名称 / 目标 / 摘要 / 文档静默丢失**，表现为"提交成功但列表多列全是 `—`"。

6. **入口必须收敛（Q5 结论：必须切）。** 主表「操作」列的 BP 动作现状走 `PlanActionModal`（单字段 `note`，`BudgetModule.jsx` 1292–1333）。页面上线后若不同步切换：**未提交过 BP 的部门**仍可从主表「操作」列写出**只含 `changeNote` 的残缺版本行**（该路径连 `payload` 都没有），同时形成"双入口两套表单做同一件事"。**收敛方案：主表 BP 动作改为跳转新页面（或打开新浮层），`PlanActionModal` 不再承接 BP。**

7. **AI 摘要是本轮最大技术风险（Q6 限制须如实告知）。** 原型**无文档解析能力**（`mock.js` 只有 `docRef` 字符串 + `docCount`），摘要只能依据**已填字段（名称 / 量化目标）改写归纳**，本质是"对一句话做扩写"，信息增量有限。因此：**生成结果必须落库为版本快照**（否则同一版本不同次渲染摘要会漂移，"版本记录"失去稳定性）；**验收标准须按"原型阶段依据已填字段归纳"降级对齐**，正式版需接入文档正文抽取。

## 四、需求基线（可直接施工版）

### 1. 页面作用域

- **粒度：一个部门 × 一个编制年**（`PLAN_FY = 2027`，`BudgetModule.jsx` 70 行）。页面 = 该部门 FY2027 全部 BP 版本列表。**不可用 `globalFy`**——年度预算计划恒为次年编制口径，`globalFy` 可切到 2026 执行年，会造成"点进去看到另一年份 BP"的错位。

### 2. 路由

| 项 | 方案 |
|---|---|
| key | **`bpplan`**（**禁用 `bp`**，见结论前置 5） |
| 路径 | `#/budget/bpplan/{deptCode}`，如 `#/budget/bpplan/D-RETAIL` |
| 注册 | `App.jsx` `MODULE_VIEWS.budget` 增 `{key:'bpplan', label:'年度 BP 计划'}` |
| 必须注册的原因 | 未注册时 `App.jsx` 168–175 行的 URL 归一 effect 会把 `#/budget/bpplan/D-RETAIL` **直接 `replace` 成 `#/budget/annual`**，页面进不去 |
| key 命名禁用清单 | `pool / bp / demand / plan / deptpool`（`App.jsx` 59–67 旧视图重定向） ∪ `annual / consume`（现行视图） |
| `MODULE_DEFAULT_VIEW` | **不改**（仍为 `annual`） |
| `SiderNav` | **不改**：其 `GROUPS` 硬编码、与 `MODULE_VIEWS` 解耦，下钻页不进左导航 |
| 定位条（面包屑） | **自动生效**，复用 `App.jsx` 289–311 定位条：`预算管理 · 编制与消耗 › 年度 BP 计划 › D-RETAIL` |
| 进出路径 | 进①主表「① 年度 BP」格；进②SUMMARY 抽屉「① 年度 BP 文档」卡片（**须改**）；出 = 页头「返回年度预算计划」→ `#/budget/annual`，浏览器后退同效 |
| 查询参数 | **不需要 `?ver=`**（无进行中版本概念）；`useHashRoute` 丢弃 `?`（`App.jsx` 83 行）**本轮不改** |

### 3. 列表 6 列（第 6 列 = 「版本」，含理由与宽度）

内容区可用宽（1440 视口、Sider 展开）：`1440 − 224 − 48 ≈ 1168`。

| # | 列 | 类型 / 取值 | 数据来源 | 可编辑 | 空态 | 宽 / 对齐 |
|---|---|---|---|---|---|---|
| 1 | **BP 名称** | string，1–60 字 | **新增 `name`** | 否 | `—` | 176 / 左，ellipsis + title |
| 2 | **年度业务量化目标** | string（自由文本，多行） | **新增 `goals`** | 否 | `—` | 200 / 左，2 行截断 |
| 3 | **BP 内容核心摘要** | string（≤300 字）或四态 | **新增 `summary` + `summarySource`** | 否 | 见 §6 四态 | 300（flex）/ 左，**2 行截断** |
| 4 | **BP 文档链接** | `[{name,url,kind}]` 或 `null` | **新增 `docs`**（由 `BP_RECORDS.docKind/docRef/docCount` 迁入） | 否 | 「未提供文档」灰字 | 130 / 左，主链接 + `+N` |
| 5 | **该版本修订说明** | string | `BP_VERSIONS.changeNote`（**已有**） | 否 | `—` | 180 / 左，**1 行截断** |
| 6 | **版本**（补） | 主行 `V1.0/V1.1…`；次行 `2026-09-22 · 陈昊` | `version` + `at` + `owner` | 否 | —（恒有） | 136 / 左，**`fixed:'right'`** |

宽度合计 `176+200+300+130+180+136 = 1122` ⇒ `scroll={{ x: 1122 }}`（窄屏兜底）。

**为什么第 6 列是「版本」而非第 1 列**（本页相对 v0.9 的调整，理由三点）：
1. **不改动用户列序**：用户原序列出 5 个内容列，前 5 列 1:1 保持其阅读顺序（名称 → 目标 → 摘要 → 文档 → 修订说明），逐条需求可按列位一一对应，评审零歧义；「版本」是分析师**追加**的系统列，追加在尾部最符合"用户没提 = 后置"的信息层级。
2. **版本号是系统产物、非业务内容**：它由 `nextMinorVersion` 生成、由排序（提交时间倒序）确定位置。置于尾部并与既有「操作」列一致地 `fixed:'right'`，横滚时行标识始终可见 —— 用户在任何滚动位置都能确认"我在读哪一版"。
3. **避免抢占（摘要列本就最宽）**：把版本放首列会把 176px 的首屏焦点让给系统字段，而本页信息量最大的是摘要；版本置于尾部使前 5 列连贯成一段可读文本流。

- 排序：**提交时间倒序**，最新版本固定首行。整表**默认只读、无行内编辑**（版本不可变）。
- **「当前版本」标识**：在版本列内用**文字自身着色 + 字重**表达 —— 当前版本 = `c.brand` + 500 字重，历史版本 = `c.t3`。**不新增列/色条/Tag**（版本号本身就是标量，"当前"只是档位；与 `PlanCell` 的"圆点承载状态、不抢焦点"哲学一致）。
- **无合计行**（版本之间不可加总）、**无「操作」列**（文档链接列自带外链动作；版本不可变，无行内操作）。
- 列表标题行右侧极简统计（12px `t3`）：`共 {n} 个版本 · 当前 {V2.1} · 最近更新 {2026-09-22 10:12}`（**派生自版本列表，不读 `BP_RECORDS`**）。

### 4. 文档链接口径（C2 推荐方案的落地形态）

`docs: [{ name, url, kind }]`，`kind ∈ {link, file}`；列内显示**主文档链接**，其余折叠为 `+N`，悬停 `title` 列出全部。**保留多文档**（理由见 §三 Q4）。

### 5. 状态机与提交语义

**状态机（刻意最小，2 态）**：

| 状态 | 含义 | 列表可见性 | 版本号 |
|---|---|---|---|
| `未提交` | 该部门从未提交过 BP | 空态 | 无 |
| `已提交` | 存在至少一个版本 | 列出全部版本 | 递增 |

```
[未提交] ──业务「修正年度 BP」提交──▶ [已提交]
                                        └── 再次提交 ──▶ 追加新版本（V1.1 → V1.2 …），旧版本保留只读
```

**与 v0.8 的关键差异（防错照搬）**：BP **无**草稿态、**无**复核/确认环节、**无**退回落差、**无**进行中版本暴露；**提交即得号**（不同 v0.8 的"复核确认后得号"）。

**提交语义**：
- **一次提交 = 追加一个版本**（不是覆盖）。版本号由 `C.nextMinorVersion(history)` 生成，首个版本 `V1.0`（**Q7 硬约束**）。
- **提交即生效**：列表首行立即出现新版本；主表「① 年度 BP」列的版本号同步刷新为最新版本。
- **历史版本不可编辑、不可删除**（本轮不提供回滚）。
- 每次提交写一条 `planActivity`（沿用 `store.jsx` 83–95 留痕机制），`stage='BP'`、`action='提交' | '更新'`、`version=新版本号`。

### 6. AI 摘要四态规则

**触发**：业务在浮层**填写了摘要** → `summarySource='business'`，AI **不介入、不覆盖**；业务**留空摘要并提交** → `summarySource='ai_pending'`，提交**立即成功**（不阻塞），AI 异步生成后回填。

```
业务提交（摘要留空）
   └─▶ 同步：写入版本行，summary=null, summarySource='ai_pending'
         └─▶ 异步：AI 生成
               ├─ 成功 ──▶ 回填 summary，summarySource='ai'
               └─ 失败 ──▶ summarySource='ai_failed'
```

**摘要列四态渲染**：

| `summarySource` | 列内展示 |
|---|---|
| `business` | 摘要正文 + 12px `t3` 后缀 `· 业务填写` |
| `ai` | 摘要正文 + 12px `t3` 后缀 `· AI 生成` |
| `ai_pending` | `AI 生成中…`（12px `t3`，可配轻量 loading 图标） |
| `ai_failed` | `AI 生成失败 · 可在「修正年度 BP」中补充`（12px `t3`） |
| `null`（老数据 / 均未填） | `—` |

- **来源标记用 12px 灰字，不用 `Tag`**（来源是摘要的附属属性，Tag 的底色/边框会与正文争夺视觉重心）。
- **必须落库为版本快照**（不是每次渲染实时生成），否则同一版本不同次打开摘要会漂移。
- **唯一允许的后置写入**：`summary / summarySource` 允许从 `ai_pending` 单向写入到 `ai` / `ai_failed`，**仅一次、不可逆**；其余字段一旦落库即冻结。
- **原型实现建议**：用前端模拟（提交后 `setTimeout(≈1.2s)` 回填模板文本），覆盖 `ai_pending → ai` 完整过程；**不要跳过异步**——"AI 生成中"恰是业务最可能追问的细节。
- **PII/保密提示（原型即须标注）**：摘要依据已填字段生成，须在浮层提示「留空将由 AI 依据本版本内容自动生成摘要」。

### 7. 「修正年度 BP」浮层规范

**组件**：新建专用浮层 `BpUpdateModal`（**不扩展** `PlanActionModal` —— 后者被 DEMAND / OPS 六个动作共用，扩展会让它们被迫接受无关键位与校验）。

**入口收敛（Q5 硬要求）**：主表「操作」列 BP 动作从 `PlanActionModal` **切走** → 改为跳转 `#/budget/bpplan/{deptCode}`（推荐）或直接打开 `BpUpdateModal`；`PlanActionModal` 不再承接 `stage==='BP'`。⚠️ 现状 `nextActionOf`（`BudgetModule.jsx` 290–295）仅在 `!r.bpDone` 时返回 BP 动作，故**双入口风险精确落在"未提交过 BP 的部门"**——正是最需要完整字段的场景。

**标题与文案**（版本号在浮层内为**只读预告**，提交后由 `store` 调 `nextMinorVersion` 确定）：

| 场景 | 标题 | 主按钮 |
|---|---|---|
| 无历史版本 | `提交年度 BP（首版 V1.0）` | 提交 BP |
| 已有历史版本 | `修正年度 BP（将生成 V{next}）` | 提交更新 |

**字段与校验**：

| 字段 | 控件 | 必填 | 校验 / 提示 |
|---|---|---|---|
| BP 名称 | `Input` | ✅ | 1–60 字 |
| 年度业务量化目标 | `Input.TextArea`（rows=3） | ✅ | 自由文本；提示：`每行一条，如「GMV：同比 +18%」`；≤500 字 |
| BP 内容核心摘要 | `Input.TextArea`（rows=4） | ❌ | 留空提示：`留空将由 AI 依据本版本内容自动生成摘要`；≤300 字 |
| BP 文档链接 | `Form.List`：每行 `名称` + `URL` | ✅ 至少 1 条 | URL 格式；支持 `+ 添加` / 删除；`kind` 由是否上传附件推导 |
| 本次修订说明 | `Input.TextArea`（rows=3） | ✅ | 写入 `changeNote`；首版默认 `首次提交` |

- `Form` `validateFields`；`cancelText="取消"`，`maskClosable` 建议 `false`（**无草稿保护，防误关丢内容**）。
- 根节点 `data-testid="budget-bp-update-modal"`。
- 提交成功反馈：`message.success('BP 已更新为 V1.2')` → 关闭浮层 → 列表刷新、新版本置顶。

**提交链路（实现约束，必须点名）**：现状 `planAction({deptCode,fy,stage,action,note,version,actor,role})`（`store.jsx` 79 行），BP 分支只映射为 `changeNote:note`（105、124 行）。新浮层须扩签名为 payload 透传：

```js
planAction({ deptCode, fy, stage:'BP', action:'提交', payload:{ name, goals, summary, docs, changeNote }, actor, role })
```

**不扩签名 ⇒ 名称/目标/摘要/文档静默丢失**，落库版本行只有 `changeNote`，表现为"提交成功但列表多列全是 `—`"——最易被误判为"渲染 bug"的实现陷阱。
