## §0 决策修订（主理人 2026-10-02 确认，覆盖本文冲突处）

本节优先级最高。凡与本文其他章节冲突之处，**以本节为准**；已被本节推翻的结论已在正文就地改正（不留补丁式说明）。

### 决策 ① —— 月份筛选的空态是合法默认态，累计范围 = FY2026 内 1 月起至最近已出账月

用户原话：「月份筛选项默认为空，列表应该如何显示是同一个问题；柱状图上的月份选中态和月份筛选控件状态联动，若月份筛选为空，则显示截至最近一个已出账月份的累计账单情况。」

**推翻的原结论**：v1.4 初稿 §7-1 提出的三个候选（60 行长表 / 部门×月矩阵 / 不支持取消）**全部作废**。累计态是唯一合法空态，不是"未初始化"，也不是"待选"。

**可实现契约**（Phase 2 直接照此实现）：

| 项 | 契约 |
|---|---|
| 空态语义 | 月份筛选**有**一个合法空态，它**就是默认态**（进入页面即为此态） |
| 空态下列表 | **截至最近一个已出账月份的累计账单情况**（按部门汇总，6 行保持不变） |
| 空态下指标卡 | 3 张卡切换为累计值：累计交付计费 / 累计运维计费 / 累计合计应收 |
| 联动方向 | **双向**：点柱 → 下拉切到该月、该柱高亮；下拉选月 → 对应柱高亮 |
| 取消路径 | **再点同一柱** 或 **下拉清空（`allowClear`）** → 回到累计态，柱选中态清空 |
| 趋势图表达 | 必须有一个「累计」视觉锚点表达空态选中（建议：基线 / 合计标记 / 累计区间底色）。**具体表达交由设计系统阶段定**，本阶段只锁定"必须有锚点"这一要求 |
| 空态下的期间动作 | 「发出账单」/「确认核销」在空态下**无明确目标月 → 建议禁用**（详见 §7-4，主理人未裁定，建议 Phase 2 采纳） |

**累计口径（已核 `mock.js` + `calc.js`，非推测）**：

| 项 | 结论 |
|---|---|
| 月份全集 | `data.months = FY2026_MONTHS` = `2026-01` … `2026-09`，共 **9 个月**（`mock.js:958`） |
| 各月账单状态 | `billStatusOf`（`mock.js:935-939`）：`confirmedMonths` = 01–07（`CONFIRMED`）；`sentMonths` = `['2026-08']`（`SENT`）；**`2026-09` 无记录 → `DRAFT`（待出账）** |
| 「最近一个已出账月」 | = 最后一个 `status !== 'DRAFT'` 的月 = **`2026-08`**。与现状 `BillingModule.jsx:128-131` 的默认月逻辑**逐字一致**（现状用的就是 `billStateOf(...) !== 'DRAFT'` 取最后一个），无需改动默认月算法 |
| **累计范围** | **`2026-01` … `2026-08`，共 8 个月**。即「**FY2026 内 1 月起累计，至最近已出账月（含）**」 |
| 明确排除 | **`2026-09` 不计入**。它是 `DRAFT`（待出账），且是当前账期 |
| `CURRENT_MONTH` 的角色 | `CURRENT_MONTH = TODAY.slice(0,7) = '2026-09'`（`calc.js:487-491`）。它**恰好**等于被排除的那个月，但**不是累计边界的定义者** —— 边界由 `billStateOf !== 'DRAFT'` 决定。⚠️ **禁止用 `CURRENT_MONTH` 推导累计范围**：一旦用户点「确认核销」把 2026-09 转为 `CONFIRMED`，`CURRENT_MONTH` 不变而累计范围应自动延到 9 个月。用 `DRAFT` 判定则两者自动同步 |
| 累计的计算方式 | **必须由 `buildBill` 逐月累加**：`Σ(m ∈ 累计范围) buildBill(data, m, dept).deliveryTotal / .opsTotal / .total`。`store.derived.monthRows` 已按月备好 `delivery/ops/total`，可加一个 `cumulative` 派生字段，**禁止在视图里另写一套累加** |

**推导出的一个设计约束**：`derived.monthRows` 的 `status` 字段必须保留 —— 累计范围要靠它过滤出"非 DRAFT 的连续区间"。若未来出现中间月为 DRAFT（历史欠账月），累计范围应是「从 1 月起**连续**的非 DRAFT 区间」还是「所有非 DRAFT 月之和」？本阶段按**后者**（求和全部非 DRAFT 月）实现，因为它对欠账月也成立；此点列为 §7-14。

### 决策 ② —— 部门筛选彻底移除，「查账」全部由《业务部门账单详情页》承接

用户原话：「所有部门查账的需求，都应该由业务部门账单详情页来承接，月度账单总览页面应该没有刚需需要一个部门筛选项，因此，移除部门筛选，就是彻底移除。」

**推翻的原结论**：v1.4 初稿 §3.3 提出的「接 Header 全局部门 Select」方案**作废**。`App.jsx:116` 的 `dept` state 与 L294-301 的 `<Select>` **保持现状不动**（它目前是死控件，只 `setState` 不下传，不起过滤作用；本轮不激活它，也不删除它 —— 删除属另一议题）。

**连带硬需求（用户明确点出，Phase 2 必须实现）**：

> 进入账单模块后想看「某个部门的钱」必须先知道它在列表第几行。若详情页不能"回到总览并定位该行"，查账链路就是断裂的。

因此**详情页必须提供一条"回总览并定位到本部门行"的路径**。实现契约见 §4.3 交互 18–19。这是本轮**仅次于决策 ① 的第二条硬需求**，不是可选优化。

**《预算消耗》页「查账」入口的目标落点**（详见 §6.6）：

| | 现状 | v1.4 目标 |
|---|---|---|
| 路由 | `#/billing/monthly/{deptCode}` | **`#/billing/bill/{billId}`**（见 §0 决策 ③ 路由裁定） |
| 落点页 | 《对账单总览》+ 自动展开 `billing-dept-ledger` + **自动打开 `Drawer` 浮层** | **《业务部门账单详情》独立页**，**不自动打开任何浮层** |
| billId 取值 | 无（只传 deptCode） | `billIdOf(最近已出账月, deptCode)`，即 `2026-08` 的那张账单，如 `BILL-202608-RETAIL` |
| 语义反转 | 详情被浮层遮住，用户看不到自己在一个页面上 | 详情页**本身就是**那个页面 |

### 决策 ③ —— 「新增 / 变更」不是总览页的信息，删卡删列都对

用户原话：「这是账单，账单是基于 digital 的项目管理系统，以及运维系统实际发生数据来统计的，因此，账单只是客观呈现情况，不存在比较，就没有所谓的新增、变更或增减；如果要提及增减，应该是在部门账单详情内，可能需要标记出哪些费用是不再年度预算规划中的，例如新增项目需求，新增系统运维费用，等」

**推翻的原结论**：v1.4 初稿 §2.2 把删卡定性为「真实信息缺口」并提出 tooltip / 保留两列的补位建议 —— **该定性与全部补位建议作废**。

**最终结论**：
- **总览页 = 客观呈现费用发生，不与年度预算规划做比较**。既然不做比较，「年度新增需求 / 变更增减」在总览页**不该存在**。
- **指标卡 3 张、列表不含新增/变更列**。
- 「哪些费用不在年度预算规划中」这类**标记**转移到《业务部门账单详情》，作为详情页的一个标记维度（§3.3）。

**术语纪律（`buildBill` 已有字段的归属分工）**：

| 字段 | 计算 | 总览页 | 详情页 |
|---|---|---|---|
| `demandType`（`年度新增需求` / `年初计划内`） | `calc.js:187`：`b.relationType === 'NEW' ? '年度新增需求' : '年初计划内'` | **不渲染** | **渲染**（标记维度，见 §3.3） |
| `changeType`（`范围 / 需求变更 ×n` / `无变更`） | `calc.js:188` | **不渲染** | **渲染** |
| `crAmount`（可正可负） | `calc.js:185` | **不渲染** | **必须渲染**（含负值，显示契约见 §3.4） |
| `newDemandTotal` / `crTotal` | `calc.js:227-230` | **不渲染** | **不直接渲染**，改由逐行标记聚合（§3.3） |

> `newDemandTotal` / `crTotal` 在总览页**不渲染但也不得留死代码** —— 视图内的 `monthAgg.newDemand` / `.cr` 累加（`BillingModule.jsx:189-190`）应随之删除。`calc.js` 的这两个字段**保留不动**（详情页与 `reconcile` 页仍在用）。

## 0bis 结论前置（5 条）

1. **决策 ③ 是本轮最重要的纠正，它改变的是"页面是什么"而不只是"页面有什么"**。总览页从"带比较语义的账单台账"变成"纯客观呈现"—— 这意味着总览页上任何带"新增/变更/同比/占比 vs 预算"色彩的文案都不该存在。Phase 2 设计时若发现自己在给总览页配比较性副标题（如"较上年增长 X%"），即是回退了。
2. **决策 ① 的空态是"累计"而非"待选"，这消除了初稿最大的未决项，但也带来一个新语义负担**：默认态下"这个数是多少"与"这个数对应哪个月"分离了。指标卡必须显式标注口径（如「累计 · 2026-01 至 2026-08」），否则用户看到一个大数却不知道它覆盖什么。
3. **累计范围是 8 个月（01–08），不是 9 个月**。`2026-09` 是 `DRAFT`（待出账）且是当前账期，必须排除。⚠️ 关键实现约束：**累计边界由 `billStateOf !== 'DRAFT'` 决定，绝不能用 `CURRENT_MONTH`** —— 用户点一次「确认核销」，`CURRENT_MONTH` 不变但累计范围应自动延到 9 个月（§0 决策 ①）。
4. **决策 ② 派生出两条硬需求，其中"详情页回总览定位本行"容易被漏掉**。它不是"体验优化"，是查账链路不断裂的必要条件（§4.3 交互 18–19）。初稿没意识到这条 —— 用户的原话把我从"信息在哪"的问题拉回到"能不能走到"的问题。
5. **详情页的标记维度存在一个真实的数据缺口**：交付侧的「年度新增需求」有现成字段（`demandType`，源自 `brds[].relationType`）；但运维侧的「新增系统运维费用」**取不到** —— `data.opsPlans` 只有 FY2027 记录、无 FY2026，而账单是 FY2026 的。如实标为待定（§3.3 / §7-9）。

## 1. 页面定位重述

### 1.1 从「按月 × 部门生成应收账单」到「全局观察 Digital 费用发生情况」

| | 现状（v1.3 及以前） | 重定义后（v1.4） |
|---|---|---|
| 回答的问题 | 「某月各部门该收多少钱」 | 「Digital 费用整体在怎么发生、谁在花」 |
| **是否做比较** | 带比较语义（新增需求 / 变更增减 / 与预算池对照） | **不做任何比较**（决策 ③）。只客观呈现两类费用发生了多少 |
| 页面主语 | 单月 × 部门 | 全年 12 个月 × 全部门；单月是列表的一个切片，空态是累计 |
| 楼层顺序 | 趋势（Card 1）→ 指标（Row）→ 月份 chip → FilterBar → 列表 | **楼层 1 = 指标 + 趋势** → 楼层 2 = 列表（仅 1 个月份下拉） |
| 详情载体 | `Drawer` 浮层（900px，盖住列表） | **独立路由页**，常驻「该部门全年 12 月流水」 |
| 明细可达性 | 先选月份、再点部门，才看得到一屏 | 直达 `BILL-` 一步到账，同页横跳 12 个月 |

**页面标题**：《对账单总览》（`月度账单` 已按决策 C 改名）。
**建议副标题口径**（供 Phase 2 参考，非定稿）：

> 全局观察 Digital 费用发生情况 —— 费用由**项目交付计费**与**系统运维计费**两类构成，均为**应收口径**：账单一旦出账即视为费用发生。页面不做预算比较。

末句"不做预算比较"是**功能性声明而非修饰**（决策 ③ 的直接后果）—— 它提前回答了用户"为什么这里没有新增/变更"的疑问。

### 1.2 两类费用的定义与计价驱动来源（已核对 `calc.js`）

> 以下全部逐行核对自 `src/domain/calc.js`，非推测。

#### A. 项目交付计费（`buildBill` 内 `lines.filter(type==='DELIVERY')`）

| 项 | 口径 |
|---|---|
| **驱动来源** | 「**交付上线**」这一个事件。以 `billMonthOf(brd) = brd.delivery.goLiveDate.slice(0,7)` 判定归属月，**不是**提报月、不是签收月、不是开发月。 |
| **计价单元** | 一条 BRD = 一行账单。逐条计价，不合并。 |
| **金额公式** | `line.amount = brdEvalAmount + brdCRDelta` = `Σ([角色,人天] × rateOf(rateCards, fy, 角色))` + `Σ(已批准 CR 的 [角色,人天增量] × 同一费率)` |
| **费率** | `rateOf` — 费率表在预算期锁定，全年不调价（`rateCards[2026]`） |
| **关键性质 1** | 金额以 **BRD 签收锁定的评估价**为准，**不是实际人天**。`actualAmount` 只是另一个字段，不参与应收金额 |
| **关键性质 2** | CR 增减是**独立计价项**，逐行标注审批人；`pricingBasis` 随之在「评估价 / 变更后价」间切换 |
| **关键性质 3** | 每行强制携带 `demandType`（`calc.js:187`）—— 这是**唯一的"计划内/计划外"分类字段**，详情页标记维度的数据源 |
| **关键性质 4** | `changeType` = `范围 / 需求变更 ×n` 或 `无变更` |

#### B. 系统运维计费（`lines.filter(type==='OPS')`）

| 计费方式 | 公式（`opsLineAmount`） | 月份相关性 | 驱动来源 |
|---|---|---|---|
| `order` 按订单量 | `round(opVolume(sys.id, dept, month) × sys.rate)` | **有** | `opVolume = VOLUME_BASE[sys][dept] × SEASON[月份] × noise`（确定性伪随机 + 12 月季节系数，取整到 50 的倍数） |
| `member` 按会员规模 | 同上（单价/单位不同） | **有** | 同上 |
| `fixed` 固定年费 | `round((sys.rate / 12) × 该部门份额 / Σ全部份额)` | **无（恒定）** | 系统年费 × 部门分摊份额 |

**关键性质（Phase 2 必须知道）**：
- 运维计费是**系统级**的：同系统对不同部门按份额/计量值分摊，**不能归因到某条需求**。这决定了它与交付计费在信息性质上根本不同 —— 交付是"项目驱动的变动成本"，运维是"系统驱动的固定/半变动成本"。趋势图叠柱合理（回答"钱从哪来"），但**不能相加解读为"同一个项目的成本"**。
- `fixed` 系统在趋势图里是**恒定水平**（与月份无关），`order/member` 才有季节波动。若不区分，用户会把运维波动全归因于"业务量变化"，而 `fixed` 部分根本不受业务量影响。
- 运维行在 `fixed` 时 `volume` 为 `null`，UI 现有口径已回退显示「固定年费 / 12」。

### 3.2 已覆盖的 4 项 —— 判定证据

**账单状态 ✅ 口径等价（主理人裁定采纳此论证）**
`billStatusOf(month, confirmedMonths, sentMonths)`（`mock.js:935-939`）**只读月份，不读部门** —— 状态是**账期（月份）级**属性，同月同状态下所有部门账单状态完全相同。因此"按状态筛选账单"在数学上等价于"按月份集合筛选账单"，而月份下拉正是这个选择器。**原筛选器在本页提供的没有任何列表维度增量，它只是在重复月份控件。**
- 补位：月份下拉选项带状态文案（`2026-07 · 已核销`）；趋势柱状态圆点保留。
- 累计态下无单一状态 → 建议在列表上方或指标区表达"已核销 7 个月 / 已发出 1 个月"。

**需求来源 ✅ 随决策 ③ 彻底移除**

**计费类型 ✅ 被列结构覆盖**
交付与运维在列表里**本来就是两列独立列**（`deliveryTotal` / `opsTotal`），零值已按淡色显示。开放状态下用户已"同时看到两类"；要"只看交付"只需看交付列 —— **筛选器在此提供零信息增量**。代价：无法隐藏运维列，但这恰恰是全局视角下不该做的（运维是 Digital 费用的重要组成）。

**关键词 ✅ 被覆盖**

### 3.3 详情页的标记维度（决策 ③ 转移过来）

用户要求：「可能需要标记出哪些费用是不再年度预算规划中的，例如新增项目需求，新增系统运维费用」

这是一个**三值分类**，需逐值核对数据可得性：

| 标记值 | 数据来源 | 可得性 | 说明 |
|---|---|---|---|
| **年度预算规划内** | 交付行 `demandType === '年初计划内'` | ✅ **现成** | `calc.js:187`：`b.relationType === 'NEW' ? '年度新增需求' : '年初计划内'`。`relationType` 来自 `mock.js:922`：`relatedDemandId ? 'PLANNED' : 'NEW'` |
| **新增项目需求** | 交付行 `demandType === '年度新增需求'` | ✅ **现成** | 同上。与上一行互为补集，**两者覆盖全部交付行** |
| **新增系统运维费用** | 运维行需要「该系统是否在 FY2026 年度运维预估内」 | ❌ **取不到** | **真实数据缺口**，见下 |

**运维侧缺口的具体证据**（已核对 `mock.js`）：

- `data.opsPlans` 的 8 条记录**全部是 `fy: 2027`**（id 形如 `OPS-2027-RETAIL` … `OPS-2027-HR`，`mock.js:560-567`），**没有任何 FY2026 的运维预算记录**。
- 而账单是 **FY2026** 的（`data.months = FY2026_MONTHS`）。**没有 FY2026 运维预算，就没有"在不在预估内"的判断基线。**
- 退一步说，即使有：`opsPlanBySystem(data, dept, 2026)`（`calc.js:503`）能算出 FY2026 的**模型派生**运维预估，但那是**按计费模型推算的**（`opsLineAmount` 同一公式 × 12 个月），与账单金额**同源同值** → 用它判断"在不在预估内"会得到**永远为"在"**的平凡结论，没有信息量。
- 因此「新增系统运维费用」在现有数据模型下**无法实现**。**如实标为待定**（§7-9），不臆造口径。

**结论：`buildBill` 的 `demandType` 足以支撑交付侧的两值标记；`changeType` 支撑变更标记。运维侧的新增标记缺基线数据，待定。**

**详情页标记维度建议结构**（Phase 2 参考）：

| 位置 | 标记 | 建议 |
|---|---|---|
| 交付明细 · 每行 | 新增项目需求 / 年度预算规划内 | 用 `Tag`（`DemandTypeTag` 组件已存在，勿新建） |
| 交付明细 · 每行 | `范围 / 需求变更 ×n`（`changeType`） | 有变更才渲染，无变更不占位 |
| 交付明细 · 汇总 | 新增项目需求小计 / 变更增减小计 | 由逐行聚合，**不直接读 `newDemandTotal`**（避免两套算法） |
| 运维明细 · 每行 | **待定** | 基线数据缺失（§7-9） |
| 运维明细 · 汇总 | 各系统金额小计 | ✅ 现成（`opsTotal`） |

### 3.4 `crTotal` 负值的正确显示契约（主理人裁定）

**既存缺陷**：`buildBill.crTotal = Σ 交付行 crAmount`（`calc.js:230`），而 `crAmount` 是**已批准 CR 的增减净额**（`calc.js:73-76`），**可以是负数**（CR 减项）。但 `BillingModule.jsx:288` 的渲染是：

```
v > 0 ? +{fmtWan(v)} 万元 : '—'
```

→ **负数（变更减少的钱）被静默显示为「—」**。这是一个把"有数据的减项"误报为"无数据"的缺陷。

**影响面收窄**：总览页已删列（决策 ③）→ 该缺陷**只影响详情页**。总览页**不得留死代码**（`monthAgg.cr` 累加随之删除）。

**详情页显示契约（三态必须可区分）**：

| 值 | 显示 | 理由 |
|---|---|---|
| **正数** | `+12.3 万元`，`c.warning` 色，带 `+` 号 | 增项：钱变多了，需要被注意 |
| **零** | `0.0 万元` 或 `无变更`，`c.t3` 色，**不带符号** | 零 ≠ 负。当前用 `'—'` 会把"恰好持平"与"无法计算"混为一谈 |
| **负数** | `−4.1 万元`（**必须带符号**），语义色建议 `c.success` 或 `c.t1` | 减项是**真实信息**（退单/冲减），绝不能显示为 `'—'` |

**关键区分**：`'—'`（`fmtWan` 对 `null`/`undefined`/`NaN` 的返回值，`calc.js:19`）**只能表示"无数据"**，绝不能用来表示 0 或负数。实施时必须区分"字段不存在"与"字段值为 0"两种情况 —— `buildBill` 的 `crTotal` 恒为数字（空数组 reduce 得 0），所以详情页里**不应出现 `'—'`**，只应出现 `0.0` 或带符号的真值。

**建议同时明确**：`changeType` 字段（`无变更` / `范围 / 需求变更 ×n`）应作为该字段的**文字说明**同行展示，让用户不靠数字也能判断有无变更。

## 5. 数据与口径约束

### 5.1 硬规则（Phase 2 实施时必须遵守）

1. **所有金额必须取自 `calc.js`，视图内禁止硬编码任何金额**，禁止自行实现计价公式。
2. **禁止"另起一套累加"**。总览页的指标卡 / 趋势柱 / 列表合计行 / 累计值**四者同源**。建议：单月值读 `derived.monthMap[M]`，累计值读**新增的** `derived.cumulative`，而非在视图内 `rows.reduce`（现状 `BillingModule.jsx:186-196`）。
3. **合计必须与列内可见值同源**：合计行 = 当前可见 `rows` 的聚合；高亮定位**不影响**合计。
4. **零值与空值区分**：`fmtWan(0)` 返回 `'0.0'`，`null` 返回 `'—'`（`calc.js:17-21`）。零金额应显示淡色 `'—'` 而非 `0.0`（沿用现状模式），但 §3.4 的 `crTotal` 是**例外**（零值必须显示 `0.0`）。
5. **累计边界禁用 `CURRENT_MONTH`**（§0 决策 ①），必须用 `billStateOf !== 'DRAFT'`。

### 7-9 「新增系统运维费用」标记缺基线数据（**最高优先级，真实数据缺口**）
