# v1.3 · 预算消耗页：移除「调整预算计划」，消耗视图退回只读

## 1. 需求

用户口头需求（2026-10-02）：「预算消耗页面的列表上，移除调整预算计划的按钮」。

确认范围：**彻底下线整条分支**（非仅隐藏入口），避免仓库里留下不可达的死代码。

## 2. 判断：为什么不是「只删按钮」

按钮背后挂着完整的一条业务链：

```
行内按钮 → Drawer → AdjustPlanForm（表单+影响预览+硬校验）
        → store.adjustProjectBudget → 改 departments.poolFY26/27
        → setPoolAdjustments → 调整流水
```

只删入口的话，链上 5 个环节全部变成不可达代码，且文件头注释仍在宣称该能力存在 ——
后续维护者会按注释去找一个点不动的按钮。因此连带移除：

| 层 | 移除项 |
|---|---|
| 视图 | `ConsumeView` 里的行内按钮、`submitAdjust`、`ctx` 状态、Drawer、`AdjustPlanForm` 组件、`ADJUST_MODE` 常量 |
| store | `adjustProjectBudget`（useCallback）、`poolAdjustments` state、value / deps 中的两处暴露 |
| mock | `POOL_ADJUSTMENTS` 常量与 `INITIAL_DATA.poolAdjustments` 字段 |
| import | `Radio`、`InputNumber`（随表单一并失效） |

**未受影响**：`ConsumeView` 的 `msgApi` prop 随之删除（唯一消费者是 `submitAdjust` 的成功提示），
其余 194 条断言里的所有预算数值**一条都没变** —— 因为 `POOL_ADJUSTMENTS` 按其自身注释
「历史记录，已反映在当前部门预算总额中（不重复叠加）」，删掉它不影响任何预算金额。
若日后要恢复调整能力，从 git 历史取回即可，数据模型无需重建。

## 3. 连带版面调整：操作列 158 → 76

原 158px 是为「查账 + 调整预算计划」两个 4/6 字 link 按钮预留的。只剩「查账」后 158px 会造成
明显空档，按内容实测量到 2 字 link 按钮 ≈ 44px + 单元格内边距，取 **76px**。

| | 列宽构成 | 合计 |
|---|---|---:|
| v0.7.2 | 116 / 132×3 / **158** | 670 |
| v1.3 | 116 / 132×3 / **76** | **588** |

`Table` 的 `scroll.x` 同步收到 588（不改会让 antd 按 670 留一段无用空白）。
合计行的 `<Table.Summary.Cell index={4} />` 不变（叶子列数仍是 5）。

## 4. 文案口径变更

「调整预算计划」在页面上的两处说明（`PageHead.desc` + 表格下方脚注）原本都把该入口当作
页面的正常能力来描述。改为显式声明只读 + 指明调整的去处：

> 点击「查账」进入账单模块查看逐笔消耗明细；**本视图为只读，预算调整在《项目预算计划》页进行。**

这不是修饰性文案 —— 页面上移除了写入口，就必须说清「为什么这里改不了、去哪改」，
否则用户会以为数据算错了。

## 5. 断言：从「分支可用」翻转为「分支确已消失」

删功能的测试方向与加功能相反：不能只把旧断言删掉了事（删掉即失去覆盖），
必须补上**反向断言**，否则回归时按钮悄悄回来也没人知道。

新增 5 条（`tests/smoke.cjs`，v1.3 段）：

1. 操作列每行**恰好 1 个** `.ant-btn` —— 用精确值而非 `> 0`，多了=入口复活，少了=查账也坏了
2. 全站文本不含「调整预算计划」/「调节额度」（含 v0.6 旧名，防旧名回流）
3. 表内 `[data-testid^="budget-consume-plan-"]` 计数为 0 且无 `budget-consume-plan-drawer`
4. 脚注含「本视图为只读」—— 只读声明真的渲染出来了
5. `budget-consume-check-D-RETAIL` 仍可点且文案为「查账」—— **反向证明减法没有把功能一起减掉**

同步改写：列宽断言（116/132×3/**76**，合计 588）、楼层二断言（去掉对 plan 按钮的依赖）。

**变异测试验证（防恒真断言）**：临时把按钮重新插回 `columns`，重建后
第 1/2/3 条**同时 FAIL**（191/194），恢复源码后 194/194 全绿 —— 证明这三条确实在咬，
不是写出来好看的空断言。

## 6. 顺带修掉的两条脆弱时序断言

删除的那段交互（点开 Drawer → 填金额 → 提交）自带约 **1.8 秒**的真实等待。
把它删掉后，下游 `v0.8.2④` 的两条断言连续 FAIL：

```
FAIL v0.8.2④：详情浮层点「编辑」→ URL 落在 #/budget/project/D-ECOM/new/{id}
FAIL v0.8.2④：列表内不再有行内编辑器（Input / InputNumber / Select 均不嵌在单元格里）
```

**定责**：与本次功能改动无关，是 `tick(340/380)` 在抽屉开合 + 路由跳转叠加 antd 动画时
本就不够的**时序脆弱断言**，被删掉的等待顺手掩盖了它。做了对照实验确认 ——
在远处补回 1800ms 后 194/194 全绿，单独跑探针该流程也通过。

**修法**：在脆弱点自身把 `340/380` 放宽到 `600`，**不在远处补一大段等待**。
后者虽然也能过测，但等于让整条时间线欠着一笔隐性负债，下次再删点什么还会复发。

## 7. 单文件产物的防假绿断言

`tests/smoke-singlefile.cjs` 补 2 条 v1.3 指纹（源码删了但没重建产物时必须 FAIL）：

* 不含「调整预算计划」
* 含「本视图为只读」

沿用 v1.2 定下的规矩：产物名与测试加载名锁同一常量，且必须用**双向**内容指纹
（含新文案 + 不含已删文案），否则会出现「一直在测旧产物」的假绿。
