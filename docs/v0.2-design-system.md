### 0.2 提炼自需求摘要的 5 个设计锚点

- **场景**：企业内部信息密集型管理后台（非营销站、非移动 App），桌面优先 ≥1280px。
- **受众**：非技术为主（业务提报人 / 负责人 / 财务），核心诉求"看得懂、算得清、追得到"。
- **调性**：企业级 / 数据密集 / 权威可信。**主学派 Tech Utility + 辅学派 Modern Minimal**；明确排除 Editorial / Brutalist / Soft Warm。
- **品牌**：迪卡侬官方 VI 主色 `#005BAA`，已有 `theme.js` 零硬编码色体系。
- **规模**：一级导航 4 项 + 二级视图 ~12 个 + 横向能力 3 项；交互复杂度中偏高。

## 1. 设计系统选型确认

### 1.1 参考风格来源：候选对比

从 71 套设计系统中，按"场景（财务型内部管理后台）+ 调性（权威可信、信息密集）+ 底座（AntD 5 + 自有品牌色）"三个筛子收敛到 3 套候选：

| 方案 | 设计系统 | 匹配度 | 特征 | 适合原因 / 不选原因 |
|---|---|---|---|---|
| **A** | **Stripe**（金融科技） | ★★★★★ | 金额为第一公民、克制的深蓝强调色、可信可审计、仪表盘式数据密度、数值右对齐 | **选定为主参考**。Stripe 是"钱的数据看板"这一品类的原型范式：它把"金额、状态、时间"的层级处理得极克制，与 `#005BAA` 的深蓝基调天然同频（都属冷蓝信任色），且其"用颜色只表达状态、不用颜色装饰数字"的原则直接命中第 4 章的去噪需求 |
| B | **Linear**（开发工具） | ★★★★☆ | 极致的表格工艺、键盘驱动、紧凑行高、冷静中性、状态点/徽标克制 | **选定为密度工艺辅参考**。Linear 的表格与列表密度标尺（行高、内边距、分隔线、悬停态）是本项目 12 个列表视图的直接工艺样板；但 Linear 偏"开发者工具"气质，作为主参考会显得过冷、过技术，不利于非技术用户 |
| C | **Vercel**（开发工具） | ★★★☆☆ | 极致中性的黑白灰、单一强调、几何栅格、预留大量留白 | **作为"表面/材质"备参考**。Vercel 的中性表面（bg1/bg2/bg3 三层灰阶）与本项目 `theme.js` 的 `bg1/bg2/bg3` 分层完全对应，可作为卡片与页面底的灰阶校准；但其极简留白倾向与"高信息密度"存在张力，只能取"材质"，不取"留白" |

> **明确排除**：Notion/Miro（协作型、偏内容编辑，非数据结算）、Nike/Spotify（消费品牌、娱乐化调性）、Tesla/BMW（汽车、视觉炫技），均与"内部财务结算需严肃可信"不符。

### 1.2 选型结论（一句话）

> **以 Stripe 为主参考风格来源、Linear 为密度工艺辅参考、Vercel 为中性材质参考；视觉学派出 Tech Utility（主）+ Modern Minimal（辅）；在 Ant Design 5 组件底座之上做"定向"，不替换组件库。**

### 1.3 视觉学派坐标

| 维度 | 定位 | 说明 |
|---|---|---|
| **主学派** | **Tech Utility（技术工具感）** | 功能至上、信息密集、多列数据表格、状态指示器、等宽数字。这是"内部结算系统"的骨。 |
| **辅学派** | **Modern Minimal（现代极简）** | 严格栅格、对齐、层级清晰、克制点缀。用于驯服 Tech Utility 的粗糙感，避免堆砌。 |
| **明确不用** | Editorial Monocle / Brutalist / Soft Warm | 娱乐化或实验性调性会削弱财务数据的严肃性；Soft Warm 的圆润大圆角/渐变更会直接制造"AI 味"（见第 5 章）。 |

### 1.4 9 段结构 · Visual Theme（视觉主题）

```
Philosophy :  财务级数据界面 —— 数字可信、状态可读、链路可追。颜色只表达状态，不装饰数字。
Direction  :  data-dense, utilitarian, precise, tabular, low-chrome
Personality:  authoritative, auditable, calm, explicit（权威 · 可审计 · 冷静 · 显式）
Reference  :  Stripe（主）· Linear（密度工艺）· Vercel（中性材质），AntD 5 为组件底座
```

**四条视觉哲学（贯穿全项目）：**

1. **数字优先**：一屏内视觉重心永远是"金额与状态"，不是装饰。金额一律等宽数字（`tabular-nums`）右对齐。
2. **颜色即语义**：品牌色 `#005BAA` 用于"当前/主操作/已核销"等结构性含义；状态色只由 `levelColor()` 与状态 Tag 产生；**不存在"为了好看而染色"的数字**。
3. **显式优于隐式**：每个金额都带单位与口径说明；每个筛选态都可见可重置；每个追溯节点都可下钻。
4. **低装饰 chrome**：1px 描边 + 平铺表面取代阴影与渐变；圆角统一 8px；无渐变、无光泽、无浮夸动效。

### 1.5 品牌提取协议（5 步法）执行记录

本项目**已有品牌资产**（迪卡侬官方 VI），执行 `brand-extraction-protocol` 如下：

| 步骤 | 执行结果 |
|---|---|
| **1. Locate** | 品牌资产 = 迪卡侬中国官方 VI 主色；载体 = `src/main.jsx` ConfigProvider + `src/theme.js` |
| **2. Download / 采集** | 主色 `#005BAA`（`colorPrimary` / `colorInfo`）；辅助状态色 `#2E7D32`（success）/ `#C77700`（warning）/ `#C0392B`（error）；表面 `#FFFFFF`（headerBg/bg1）/ `#F5F7FA`（headerBg 表格头）/ 灰阶 `bg1–bg3`；文本 `t1 #1F2937` 系 |
| **3. Grep Hex** | 已提取：`#005BAA` `#2E7D32` `#C77700` `#C0392B` `#FFFFFF` `#F5F7FA` `#1F2937`（详见第 2 章表格，含 OKLCh 近似值） |
| **4. Codify** | 编码为第 2 章的 Design Tokens（HEX + CSS 变量双格式），作为 `brand-spec` 并入项目令牌表 |
| **5. Vocalise** | **品牌视觉语言**：迪卡侬蓝是一支"运动、可靠、非金融"的蓝 —— 它不追求 Stripe 紫蓝的科技感，也不追求银行深蓝的沉重感，而是"户外装备"的中性可靠蓝。因此在本项目中：品牌色只做"结构性锚点"（导航高亮、主按钮、已核销口径、链接），绝不做大面积背景填充，也不做渐变，以保持内部结算系统的克制与严肃。 |

> **关键判断**：`#005BAA` 与 Stripe 蓝、Linear 蓝同属冷色信任系，因此"主参考 Stripe"不会与自有品牌冲突 —— 我们取 Stripe 的**信息架构与克制原则**，不取其具体色值。

### 2.2 排版规范

#### 2.2.1 字体栈（继承 main.jsx，全项目统一）

```css
--dkt-font-sans : -apple-system, BlinkMacSystemFont, 'Segoe UI', 'PingFang SC', 'Microsoft YaHei', sans-serif;
--dkt-font-num  : ui-monospace, 'SF Mono', 'JetBrains Mono', 'Roboto Mono', Menlo, Consolas, 'PingFang SC', monospace;
```

- **正文/标题**：`--dkt-font-sans`（中文优先 PingFang SC / Microsoft YaHei）。
- **金额/编号/日期**：**不换字体族**，改在 `font-sans` 上加 `font-variant-numeric: tabular-nums;`。理由见下。

> **关键取舍**：v0.1 的 `useT().fontNum = token.fontFamilyCode` 直接给金额套等宽字体族，跨平台不一定命中（中文环境常回退）。v0.2 规则改为：**金额数字 = 正文 sans + `tabular-nums`**（保证数字等宽对齐与小数点对齐），**仅单号/编号（DM-/BRD-/CR-/BILL-）与费率使用 `--dkt-font-num`**。这样既满足"金额必须等宽数字"，又避免中文金额单位（万元）被等宽字体拉宽。

#### 2.2.2 字号阶梯（字重仅 400 / 500 两档）

| 层级 | 字号 | 字重 | 行高 | 用途 |
|---|---|---|---|---|
| 页面标题（PageHead） | 18px | **500** | 1.4 | 二级视图名 |
| 主指标数字（L1） | 22px | **500** | 1.2 | KPI 卡主数字（金额） |
| 小节标题（BlockTitle） | 14px | **500** | 1.5 | 卡片内区块标题 |
| 卡片小指标（L2） | 16px | **500** | 1.3 | Statistic 小数字 |
| 正文 / 表格主字段 | 13–14px | 400 | 1.5–1.6 | 表格单元格、描述项 |
| 表格内金额（L3） | 13px | 400 | 1.4 | 金额单元格（tabular） |
| 辅助 / 单位 / 说明（L4） | 12px | 400 | 1.5 | 单位"万元"、口径说明、时间 |
| 微标签 | 11px | 400 | 1.4 | 部门代码、次级 meta |

> **⚠ 与 v0.1 的偏差修正**：v0.1 多处使用 `fontWeight: 600`（如 `Metric` 数字、App Logo）。v0.2 统一收敛为 **仅 400 / 500**：所有 600 降为 500；强调靠**字号 + 颜色/层级**，不靠字重堆叠。**prototype-builder 落地时须将存量 600 替换为 500。**

#### 2.2.3 金额排版铁律

```css
.amount { font-variant-numeric: tabular-nums; font-feature-settings: 'tnum' 1; text-align: right; }
```

1. **一切金额/人天/百分比/计量值必须 `tabular-nums` 且右对齐**（列表、卡片、描述、Tooltip 内均适用）。
2. 金额单位"万元"用 12px `t3` 紧随数字，**不换行**（`white-space: nowrap`）。
3. 正负号显式化：偏差用 `signedPct()`（`+X% / -X%`），避免只见数字不见方向。
4. 负数/透支金额用 `danger`，其余金额用 `t1`（**不用品牌色给普通金额染色**，见第 4 章）。

### 2.3 色彩使用规则

| 场景 | 允许 | 禁止 |
|---|---|---|
| **品牌色 `#005BAA`** | 一级/二级导航当前项；主按钮；文字链接；"已核销"口径段与图例；可点击单号；进度条主段 | ❌ 大面积背景填充 / ❌ 渐变 / ❌ 给普通金额染色 / ❌ 装饰性色块 / ❌ 曲线图多条线同用品牌色 |
| **状态色** | 仅由 `levelColor()`（ok/watch/warn/over）与状态 Tag（`BrdStatusTag` / `BillStatusTag` / `DemandTypeTag`）产生 | ❌ 在业务组件里手写 `color="#2E7D32"` 之类；❌ 用状态色表达非状态含义（如用 danger 表达"重要"） |
| **文本色** | `t1` 正文/数字、`t2` 次要、`t3` 说明/单位、`t4` 禁用 | ❌ 用品牌色写大段正文；❌ 用状态色写整段说明文字（只用其 `*Text` 变体做关键词强调） |

#### 3.2.1 统一模式

**位置**：板块二级导航之下、内容卡片之上，**通栏一行**；与表格**同属一个卡片或紧邻**，视觉上"筛选 → 结果"成对。

#### 3.2.3 默认值展示 & "已筛选"状态

- **默认值 = 最宽口径**：全部/全年/所有状态，控件显示占位文案（如"全部部门"），**不以灰字暗示有默认筛选**。
- **"已筛选 N 项" 指示**：当存在**非默认值**的筛选时，右侧出现胶囊 `● 已筛选 N 项`（底 `filterChipBg`，点 `filterDot`，12px）。
- **重置入口**：状态区最右固定 `重置` 文字按钮；无任何非默认筛选时**禁用**（灰）而非隐藏，保持位置稳定。
- **结果计数**：`共 N 条`（tabular），紧邻"已筛选"，二者与"重置"间距 `space-4`。

#### 3.2.4 与表格的关系（职责边界）

1. FilterBar 是**唯一上游**：筛选状态存于页面 state，`dataSource = 原数据.filter(...)`。
2. **禁止把筛选控件放进表格工具栏/表头**（避免两处筛选），表头只保留排序。
3. 表格 `pagination` 显示 `showTotal`（`共 N 条`），与 FilterBar 计数**同源**，不允许各算各的。
4. **空态**：`Blank` 组件须带"清除筛选"引导（`该条件下暂无数据 · [重置筛选]`），而不是干瘪的"暂无数据"。
5. 筛选变化**不重置分页到第 1 页以外**——回到第 1 页（避免"筛选后停在空白页"）。

### 3.3 溯源链组件 TraceChain（本平台最有辨识度的组件）

> Ant Design **没有**现成的六节点、带状态、可下钻的横向链路组件。`Steps` 只能表达"线性进度"（当前步 + 未到步），无法同时表达"每节点的值 + 已完成/进行中/未开始/异常四态 + 逐级跳转"。**方案：以自定义 Flex 布局为主，`Steps` 为降级备选。**

#### 3.3.1 节点定义（6 节点固定）

```
① BP归档 ──▶ ② 年度需求 ──▶ ③ BRD提报 ──▶ ④ 评估签收 ──▶ ⑤ 交付上线 ──▶ ⑥ 月度账单
```

| # | 节点 | 主值来源（calc 接口） | 下钻目标 |
|---|---|---|---|
| ① | BP归档 | `traceOfBrd().bp` → `version` + `status` | 预算管理 > 业务规划 BP（`?bp=BP-2026-RETAIL`） |
| ② | 年度需求 | `traceOfBrd().demand.id`（或"年度新增"） | 预算管理 > 年度需求清单（`?demand=DM-2026-0031`） |
| ③ | BRD提报 | `brd.id` + `submitDate` + `relationType` | 项目管理 > 需求受理（`?brd=`） |
| ④ | 评估签收 | `brd.signedDate` + `evalAmount` | 项目管理 > 评估与签收（`?brd=`） |
| ⑤ | 交付上线 | `brd.delivery.goLiveDate` + `evalMD/actualMD` | 项目管理 > 交付与偏差（`?brd=`） |
| ⑥ | 月度账单 | `billId` + `billStatus` + `amount` | 计费账单 > 月度账单（`?bill=BILL-202607-RETAIL`） |

#### 3.3.2 视觉规格（节点卡 + 连接器）

```
┌──────────────┐    ┌──────────────┐    ┌──────────────┐
│ ① BP归档   ✓ │───▶│ ② 年度需求 ✓ │───▶│ ③ BRD提报 ● │─ ─ ─▶ …（未开始用虚线）
│ BP-2026-RTL  │    │ DM-2026-0031 │    │ BRD-2026-105 │
│ V3 · 已归档  │    │ 预估 42.0万   │    │ 2026-03-12   │
└──────────────┘    └──────────────┘    └──────────────┘
  已完成(实线+品牌)    已完成(实线+品牌)     进行中(品牌描边+外环)
```

| 元素 | 规格 |
|---|---|
| 节点卡尺寸 | 宽 **128px**，高约 **64px**，圆角 8px，1px 描边 |
| 节点内三行 | 行1：序号 + 节点名（12px/500，`t1`）；行2：主值（12px，`t1`，单号用 `--dkt-font-num`）；行3：meta（11px，`t3`，日期/金额 tabular） |
| 连接器 | 宽度 `24px`，居中一个 `→`（12px）；**已完成段实线 `brand`；未开始段虚线 `t4`** |
| 横向溢出 | 6×128 + 5×24 ≈ **888px**，任何详情抽屉（≥720px）均可容纳；窄于该宽度时按 3.3.5 降级 |

#### 3.3.3 节点状态表达（四态）

| 状态 | 判定 | 节点视觉 | 连接器（其右侧） |
|---|---|---|---|
| **已完成** | 该阶段有完成时点（BP 已归档 / 需求已定稿 / BRD 已提报 / 已签收 / 已上线 / 账单已核销） | 描边 `brand` + 底 `chainDoneBg` + 左上角 ✓ 徽标（`success`） | 实线 `brand` |
| **进行中** | 当前所在阶段（有值但未完成，如 BRD 已提报未签收、账单已发出待确认） | 描边 `brand`（2px）+ 外环 3px `chainActive` @20% + 左上角 ● 脉冲点 | 虚线 `brand` @50% |
| **未开始** | 无值（如未上线、未出账） | 描边 `border` + 底 `bg3` + 文字 `t3` | 虚线 `t4` |
| **异常** | 该阶段被驳回（`brd.status==='REJECTED'`）或账单有申诉 | 描边 `chainError` + 左上角 `!` 徽标（`danger`） | 断路：连接器 `danger` + 中间断开样式 |

> **状态推导的唯一来源**：`calc.traceOfBrd()` / `traceOfDemand()` 的返回字段，**组件内不得自行判断业务状态**。给出映射表（供 prototype-builder）：

| 节点 | 已完成 | 进行中 | 未开始 | 异常 |
|---|---|---|---|---|
| ① BP归档 | `bp.status==='已归档'` | `编制中/已提交` | `bp===null` | — |
| ② 年度需求 | `demand.status!=='待评审'` | `待评审` | `demand===null`（→ 显示"年度新增"灰态） | — |
| ③ BRD提报 | 有 `brd.id` | `SUBMITTED/EVALUATING` | — | `REJECTED` |
| ④ 评估签收 | `brd.signedDate` | `status==='SIGNED'` 未付 | 未签收 | — |
| ⑤ 交付上线 | `brd.delivery` | — | 未上线 | — |
| ⑥ 月度账单 | `billStatus==='CONFIRMED'` | `SENT` | `DRAFT`/无 | 有争议 |

#### 3.3.4 交互规则

1. **每个节点可点击** → 跳转到对应视图并定位对象（`onNavigate` / hash 深链）。未开始节点可点击但目标页给出"该环节尚未发生"空态。
2. **节点 hover** → Tooltip 显示该节点金额/人天/日期细节；指针为 `cursor:pointer`。
3. **当前锚点高亮**：进入某对象详情时，**该对象所在节点**加"锚点环"（区别于"进行中"脉冲），明确"你正在看的是这个环节的这条数据"。
4. **账单项溯源**：账单行内嵌"溯源链跳板" —— 一个 `①→②→③` 的极简三节点缩略 + "查看完整链路"链接，点击展开完整 6 节点（避免在表格行内塞 6 节点撑高行高）。
5. **年度新增需求（无溯源）**：② 节点渲染为灰态"年度新增（无年初需求）"，并在链路下方给一行 12px `warning` 说明，而非隐藏节点——保持链路骨架的完整性（这是产品原则，见 DESIGN.md 2.1）。

#### 3.3.5 响应式降级

| 容器宽度 | 形态 |
|---|---|
| ≥ 900px | 6 节点单行（默认） |
| 640–900px | 折行为 **3 + 3 两行**，行尾以 `↴` 连接 |
| < 640px | 切换为 Ant `Steps direction="vertical"` 或 `Timeline`，每节点 description 承载主值 |

| # | 问题 | 影响 |
|---|---|---|
| P1 | 已承诺段用 `c.info + opacity:0.55` 透明叠加 | 在白卡片 vs 灰页面上观感不一致，像渲染 bug |
| P2 | "已规划"仅一条虚线，无悬停值、无顶部标记 | 用户看不出"已规划会超包多少" |
| P3 | 无 100% 刻度基准线 | 透支时无法直观判断"超出多少" |
| P4 | 可用段纯透明 | 空槽与"可用为 0"难以区分 |
| P5 | 无无障碍标签 | 屏幕阅读器只能读到一堆积木 |
| P6 | 表格内（无图例）与详情卡（有图例）两形态数值口径标注不一致 | 用户需回看说明 |
| P7 | 透支时 `base = max(total, used)` 压缩了各段比例 | 正常态的比例感在透支态失效（见下方案修正） |

#### 3.4.2 v0.2 改进规范

**统一结构**（高度三档：8px 表格内 / 12px 默认 / 16px 详情卡）：

```
0%                     50%                    90%      100%   planned↑
├────────┬──────────────┬──────────────────────┼────────┼──────────┤
│已核销  │ 已承诺       │      可用（空槽）     │ 预警线 │ 透支(斜纹)│
│(brand) │(meterCommitted)                      ↑100%刻度   (danger)
└────────┴──────────────┴──────────────────────┴────────┴──────────┘
                                                     ▲ 已规划虚线 + 顶部三角
```

**改进项清单：**

| # | 改进 | 实现要点 |
|---|---|---|
| I1 | 已承诺改用**实色 `meterCommitted`（`#7FA8CC`）** | 去掉 opacity 叠加，任意底一致 |
| I2 | 可用段用**浅底 `meterTrack`** 而非透明 | 空槽可辨识；`used===total` 时可用段消失 |
| I3 | 增加 **100% 刻度线**（`borderStrong` 1px 竖线） | 透支时右侧段以斜纹（`repeating-linear-gradient` danger）表示超出部分 |
| I4 | 已规划标记升级：**虚线 + 顶部小三角**（`meterPlanned`） | 悬停显示"已规划 X 万元，若全部落地将超包 Y 万元" |
| I5 | 每个段加 `aria-label`（如 `已核销 320.5 万元`），容器 `role="img"` | 合并为一句可读摘要 |
| I6 | 图例数值统一**右对齐 tabular**，并加口径 caption | 图例下补一行 12px `t3`："可用余额 = 总包 − 已承诺 − 已核销（已规划不计入）" |
| I7 | **比例基准修正**：正常/关注/预警态 `base = total`；透支态 `base = used`（把已承诺 + 已核销压缩进 100%，透支段显式溢出） | 保证两态都有稳定的必读信息 |
| I8 | 两形态统一：`showLegend` 切换，但**口径 caption 常驻** | 表格内至少保留迷你图例（色点 + 名称） |

**节点语义色（复用 `levelColor`，不引新色）**：`meterBilled=brand`、`meterCommitted=#7FA8CC`、`meterOver=danger`、`meterTrack=bg3`、`meterPlanned=warning`。

## 4. 信息密度与层次规则

### 4.1 一屏内首屏必须传达什么（每个视图的"黄金三角"）

任何列表视图首屏，**自上而下固定三带**：

1. **标题带**（PageHead）：视图名 + 一句话职责 + 关键口径说明（"数据截至 2026-07 已结账月份"）。
2. **指标带**：**2–4 个 Metric 卡**（L1 数字 22px/500）。这是"总"。
3. **操作带 = FilterBar + 表格**：这是"分"。筛选与结果成对出现。

> **首屏规则**：用户不滚动就能回答"这块现在什么状况（指标带）+ 我关心的是哪几条（筛选 + 表格头部几行）"。

### 4.2 "总—分"层次组织

| 层 | 载体 | 数量约束 |
|---|---|---|
| 总（全公司/全年度） | 顶部 Metric 卡带 | ≤ 4 张 |
| 分（部门/系统/需求） | 主表格 | 一屏一个主表格；最多再叠一个"下钻/明细"次级表格 |
| 细（单对象） | **抽屉**（不新开页） | 详情一律用 Drawer，保持列表上下文 |

- **主表格只放"可比较的一列数值"**；单对象的复杂明细（人天拆解、账单行、CR 明细）下沉到抽屉。
- 卡片嵌套**最多 2 层**（卡片内可以有 Hint/Table，但不再嵌套第三个带描边的卡）。

### 4.3 KPI 卡 / 表格 / 趋势图的使用边界

| 载体 | 用于 | 不用于 |
|---|---|---|
| **Metric 卡** | 少量（≤4）关键**总额/总量**指标，需一眼看到 | ❌ 承载需要对比的多个对象（那是表格） ❌ 承载时间序列 |
| **表格** | 多对象横向对比、精确到行、需排序/筛选 | ❌ 只展示 1–2 个数（用卡片） ❌ 展示趋势 |
| **趋势图 / 迷你条** | **≥ 3 个时间点**的走向（月度消耗趋势）；或单值占比（`Progress` 迷你条） | ❌ 单期对比（用水平条/进度条） ❌ 装饰性环形图 |

- 折线/柱状图**通篇一个组件库口径**（本项目用 AntD `Progress` + 轻量自绘迷你条，不引入 echarts，控制包体与风格统一）。
- 图表**必须有基准与口径**（Y 轴单位、时间范围），否则宁可不画。

### 4.4 同页多金额的"去噪"规则（重点）

平台处处是金额，是视觉噪音的高发区。强制以下 4 条：

1. **一区一主数字（Hero Number）**：每个卡片/区块内，**只有 1 个 L1（22px）数字**；其余金额降级为 L2/L3。
2. **颜色纪律（最关键）**：**只有"需要被注意"的金额才染色**（负值/透支 → `danger`，待处理 → `warning`）。
   - ✅ 正确：8 个部门里，只有"透支的 1 个"用 `danger`，其余 7 个 `t1` 黑。
   - ❌ 错误：每张 KPI 卡配不同鲜艳色（彩虹卡）——这是第 5 章的头号陷阱。
3. **口径可见**：任何金额旁必须有单位或口径标签（"万元"/"已核销"/"预估"）；**两个不同口径的金额不得相邻而无标签**（如"已承诺 120.0" 与 "已核销 98.5" 必须各带标签与图例色点）。
4. **对齐即降噪**：同一列/同一组金额**右对齐 + tabular-nums**；小数点对齐本身就是最强的降噪手段。

> **反例自检**：若一屏内**染色金额 > 3 处**，说明"重要性判断"失效，必须重新排序重要性、只保留最关键的染色。

## 5. Anti-Slop 自查（本项目最易出现的 5 个"AI 味"陷阱）

| # | 陷阱 | 长什么样（反面） | 为什么会发生 | 规避方式 |
|---|---|---|---|---|
| 1 | **彩虹 KPI 卡** | 4 张指标卡各配一个高饱和色（蓝/绿/橙/紫），像仪表盘主题包 | AI 默认"让每个卡都好看" | **单色系 + 仅状态着色**：KPI 卡数字默认 `t1`，只有负值/透支/待处理才 `danger`/`warning`；品牌色只给"主口径"1 处 |
| 2 | **过度圆角 + 阴影 + 渐变** | `radius 16–24`、彩色投影、卡片渐变底、按钮渐变 | 训练数据里"现代感"= 圆角阴影渐变 | **硬约束**：`radius 8`、**无阴影、无渐变**、描边 1px；浮层才允许 Ant 默认阴影 |
| 3 | **装饰性/无意义图标与 emoji** | 标题前堆 emoji、每个标签配图标、空态放插画 | "看起来更丰富"的错觉 | **图标只承载语义**（状态/方向）；禁用 emoji；状态用 `BrdStatusTag` 的语义图标（✓/⏱/!/—）即可 |
| 4 | **营销站式大留白 + 大标题** | 40px 标题、巨大 padding、一屏只放 3 个元素 | 把"简洁"误解为"空" | **内部后台 = 高密度**：页面标题 18px、卡片 padding 16–20、行高 36；一屏应承载"指标 + 列表头部多行" |
| 5 | **编造数字 / 装饰性数据** | 图表里出现无法溯源的美化数字、"预计增长 +37%"之类无源结论 | AI 倾向于"补全一个漂亮的数字" | **一切金额唯一真相 = `calc.js`**；页面禁止自算金额（需求摘要硬约束 1）；无源则显示 `—`，绝不编造 |

**额外红线（虽不入 Top5，但同类）**：① 紫蓝"科技渐变"；② 中文用圆润的英文展示字体（Inter/Poppins 直接套中文，字面发虚）；③ 无差别的 `loading` 骨架屏刷满全屏；④ 自定义滚动条美化。**一律禁用。**

**自查口诀（交付前逐条过）**：
> 数字是否对齐且等宽？→ 一屏染色金额是否 ≤3？→ 有无渐变/大阴影/大圆角？→ 每个图标是否都有语义？→ 每个金额是否都能追到 `calc.js`？
